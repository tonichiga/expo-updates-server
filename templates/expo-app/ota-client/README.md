# Installation telemetry client

Generated by `configure-app`; update the server template and rerun configuration to upgrade it.
Build and install a new native binary when first adding this client: it requires
expo-updates, expo-application, expo-crypto, expo-secure-store and AsyncStorage. Do not deliver newly
required native modules to an older binary via OTA. Keep these native dependencies
in the same runtime compatibility boundary as the rest of your application.

`ota-entry.js` starts telemetry without waiting, then synchronously loads the original
entry saved in `ota-client-entry.json`. The configurator also patches the root layout with the update hook and gate. Development,
Expo Go, web and disabled-updates builds do not report. Original OTA check policy
remains under the application/configurator's control.

The public API exports `start()`, `getInstallationId()`, `checkForUpdateAsync()` and
`fetchUpdateAsync()`. The latter two wait for durable identity and the installation_id
Expo extra parameter. Direct Expo calls at module startup do not have this guarantee.
Telemetry failure never waits on network before returning identity.

State is a single AsyncStorage envelope: installation ID, increasing sequence and
one pending event. Writes/acks serialize; network requests have an 8-second timeout.
Startup and active foreground report the current launch; active timers refresh no
more often than once per minute. Failures retry with capped backoff (up to 5 minutes).
One latest pending snapshot bounds offline storage; it is not an exhaustive offline
transition history. Only accepted receipts refresh server last-seen time.

The ID identifies an installation, not a person or a permanent physical device.
Clearing app data/reinstallation may change it; OS backup/restore may copy it. Never
use this self-reported ID as authorization. No admin/database/storage secrets belong
in this directory. Heartbeat indicates JS startup, not successful smoke testing.

## Device-targeted releases

The entry bootstrap also initializes a separate Device ID automatically. Android uses a
SHA-256 hash of app-scoped Android ID; iOS uses a random seed in SecureStore/Keychain.
Both are scoped to application ID and `config.json.identityNamespace`. Keep that namespace
stable when changing tunnel URLs. Runtime/channel changes do not change Device ID.
Installation ID still changes on reinstall and remains the unit of telemetry.

Device ID may survive reinstalls, but is not guaranteed across factory reset, signing key
changes or iOS Keychain deletion. Raw Android IDs never leave the device. If identity is
unavailable, the server only offers public or explicitly installation-targeted releases.

`getDeviceId()` is optional for displaying diagnostics. `start()` is already called by the
generated entry; telemetry works independently of the root hook. Custom check/download UI should use the
exports here, which await identity initialization before calling Expo. Direct Expo calls
made too early are anonymous. Rebuild the native app with a new runtime after adding
SecureStore; do not deliver this client to older binaries lacking the native dependency.

## Update hook

`useOtaUpdates` shares identity, state and lifecycle actions across the application.
The configurator inserts it and `OtaUpdateGate` in the root layout automatically.
See [Update lifecycle](./docs/update-lifecycle.md) for manual/automatic/background
updates, force OTA versus store upgrades, custom guards and option defaults.

For a custom root that could not be patched, see the complete
[manual integration guide](https://tonichiga.github.io/expo-updates-server/ota-client-lifecycle#manual-integration)
(or `docs/ota-client-lifecycle.md` in the server repository). It covers both an
already generated client and copying/configuring the client without the generator.
