# Статистика установленных OTA и адресная доставка обновлений

Дата исследования: 2026-10-15. Проверены официальная документация Expo и исходники `expo/expo/main`. Это исследование и предложение архитектуры; описанные ниже новые функции пока не реализованы. Поведение конкретного мобильного приложения нужно сверить с его фактически установленной версией `expo-updates`: код `main` не является обещанием поддержки в старых SDK.

Дополнение 2026-10-16: реализован первый подготовительный кандидат — защита соответствия manifest ID конкретному update ID. Исходный аудит ниже сохранён как описание состояния до исправления. Heartbeat, статистика и аудитории остаются следующими этапами. Порядок обновления описан в [operations guide](../operations-guide.md#manifest-identity-migration-2026-10-16).

## Вывод

Для сценария «выпустить OTA только на мой телефон, проверить, затем открыть остальным» нужен серверный выбор аудитории обновления и идентификатор установки. Для решения «какие версии поддерживать» нужна отдельная телеметрия фактически запущенной версии. Счётчик загрузок не заменяет эту телеметрию. Рекомендуемый первый этап: стабильный `installationId`, событие запуска/heartbeat, allowlist установок для кандидата и отдельное действие продвижения кандидата в публичную раздачу.

## Что предоставляет Expo

`Updates.updateId` идентифицирует выполняемый update; `Updates.runtimeVersion` — native runtime текущей сборки. `Updates.isEmbeddedLaunch` отличает встроенный JS от OTA, `Updates.isEmergencyLaunch` и `emergencyLaunchReason` — аварийный fallback. При выключенном updates/dev-режиме некоторые значения отсутствуют. `checkForUpdateAsync()` проверяет наличие, `fetchUpdateAsync()` скачивает, `reloadAsync()` запускает скачанное; без reload оно применяется при следующем cold start. Сам факт завершения fetch не подтверждает запуск. Большинство этих API следует проверять в release-сборке. [Expo Updates API](https://docs.expo.dev/versions/latest/sdk/updates/).

Store version и номер native build — отдельные измерения: `Application.nativeApplicationVersion` и `Application.nativeBuildVersion`. Их следует брать из native-приложения, чтобы не смешивать версию установленного бинарника с конфигурацией JS-обновления. [Expo Application API](https://docs.expo.dev/versions/latest/sdk/application/).

OTA совместимо только с подходящими native runtime и платформой; новый JS не устанавливает новую native-сборку. Channel описывает поток обновлений, а не уникальный телефон. Поэтому перевод между несовместимыми runtime означает установку новой версии из магазина; адресная OTA-раздача должна сохранять ограничения совместимости. [How EAS Update works](https://docs.expo.dev/eas-update/how-it-works/).

## Идентификатор установки и адресная доставка

Публичный API — `await Updates.setExtraParamAsync('installation_id', installationId)`. Название в единственном числе: **setExtraParamAsync**, не `setExtraParamsAsync`. Чтение — `getExtraParamsAsync()`. Параметры передаются в заголовке `Expo-Extra-Params` как Structured Field Value Dictionary; это не query string и не JSON. Сервер вправе использовать их для выбора OTA. [Expo Updates API](https://docs.expo.dev/versions/latest/sdk/updates/#updatessetextraparamasynckey-value).

Extra params сохраняются в native SQLite в области `scopeKey`; Android-реализация валидирует их сериализацию и имеет операцию очистки при сбросе build data. Рекомендация: хранить собственный случайный UUID установки отдельно и восстанавливать параметр перед ручной проверкой обновлений. [ManifestMetadata.kt](https://github.com/expo/expo/blob/main/packages/expo-updates/android/src/main/java/expo/modules/updates/manifest/ManifestMetadata.kt).

Текущие реализации Android/iOS также отправляют `EAS-Client-ID`, `Expo-Current-Update-ID`, `Expo-Embedded-Update-ID`, а при наличии сведений — `Expo-Recent-Failed-Update-IDs`. Они полезны для диагностики и серверной оценки текущего состояния. Не следует считать их доказательством успешного smoke-теста или полагаться на обязательное присутствие во всех старых клиентах. [Android FileDownloader](https://github.com/expo/expo/blob/main/packages/expo-updates/android/src/main/java/expo/modules/updates/loader/FileDownloader.kt), [iOS FileDownloader](https://github.com/expo/expo/blob/main/packages/expo-updates/ios/EXUpdates/AppLoader/FileDownloader.swift).

Рекомендуемый контракт:

1. Приложение создаёт UUID установки и показывает его в диагностическом экране, откуда владелец может скопировать его в админку.
2. До update-check устанавливает `installation_id` через `setExtraParamAsync`; тот же ID передаёт в телеметрии.
3. Сервер сопоставляет установку с allowlist конкретного deployment. Присланный ID — селектор, не самостоятельное доказательство права доступа. Для непубличных артефактов добавить подтверждённую регистрацию/токен установки; не принимать клиентское `isTester=true` как разрешение.
4. Неизвестные клиенты получают только текущий публичный релиз. Неподходящая платформа/runtime не обходится allowlist.
5. Разрешение на кандидата изменяется на сервере. Мобильное приложение сообщает идентичность, а не выбирает себе привилегированную аудиторию.

UUID здесь означает **установку приложения**, а не физический аппарат навсегда. Переустановка/сброс данных и backup/restore требуют явно выбранной политики жизненного цикла. Для двух телефонов одного человека — два ID. Для числа людей нужен отдельный, опциональный `userId` и отдельный отчёт: один пользователь может иметь разные версии на разных установках.

### Нужны ли overrides заголовков или каналов

Для собственного сервера с extra params — нет. `setUpdateRequestHeadersOverride()` доступен начиная с SDK 54 / `expo-updates` 0.29.0; переопределяемые headers должны быть объявлены в native build, а переданный объект заменяет весь набор custom headers. Вариант `setUpdateURLAndRequestHeadersOverride()` появился в SDK 52 / 0.27.0 и требует `disableAntiBrickingMeasures`; Expo рекомендует его для preview, не production. Он избыточен для описанного сценария. [Override update configuration](https://docs.expo.dev/eas-update/override/).

## Что считать в статистике

Рекомендуемый основной показатель: «Последняя наблюдавшаяся запущенная версия у уникальных установок, активных за 7/30 дней». Он даёт основание решать, какие runtime ещё поддерживать. Показывать дату последнего контакта и покрытие телеметрией; offline и старые клиенты без instrumentation не исчезают из реальности только потому, что сервер их не видит.

| Поле | Назначение |
| --- | --- |
| `installationId`, опционально `userId` | Установка и человек учитываются отдельно |
| `appId`, `platform`, environment/channel | Изоляция приложений и контуров |
| `nativeApplicationVersion`, `nativeBuildVersion` | Какие магазинные версии используются |
| `runtimeVersion` | Какие native runtime нужно поддерживать |
| `runningUpdateId`, `isEmbeddedLaunch` | Какая JS-версия действительно исполнялась |
| `isEmergencyLaunch`, `emergencyLaunchReason` | Наблюдаемые аварийные возвраты |
| `eventId`, `sessionId`, `observedAt`, server `receivedAt` | Дедупликация, время события, запоздавшая доставка |
| `lastSeenAt`, опционально `appReadyAt` | Активность и прохождение инициализации |

Событие отправлять после старта JS; отдельно `app_ready` после нужного приложению этапа инициализации и heartbeat при foreground с ограничением частоты. Доставлять через локальную очередь с повторными попытками, дедуплицировать по `eventId`; поздние события не должны откатывать «текущую версию» на устаревшую. Серверное время получения полезно для freshness, но не определяет порядок offline-запусков: предусмотреть session sequence/время наблюдения и явные правила конфликтов.

Рекомендуемые отдельные состояния: сервер предложил → клиент скачал → новый update запустился → приложение готово. Ошибка fetch, rollback и отсутствие дальнейшего heartbeat — разные события. Ошибка до JS может не позволить отправить телеметрию: дополнить crash reporting/native-логами, а не трактовать молчание как успешный запуск.

Для каждого runtime и OTA показывать уникальные активные установки, долю от выбранного активного окна, embedded/OTA, динамику переходов и ошибки. Одна установка учитывается один раз по последнему достоверному состоянию в таком отчёте; отчёт о «хотя бы одном запуске версии за период» имеет другой смысл и может учитывать её в нескольких версиях.

Expo также различает грубую оценку по update-check requests и более точные клиентские события запусков: это прямо отражено в EAS Insights. Однако его облачные отчёты не превращают custom server автоматически в аналитический сервис. [EAS Insights: App usage](https://docs.expo.dev/eas-insights/app-usage/).

## Smoke → всем: рекомендуемая семантика

Разделить **артефакт** (bundle/assets) и **deployment** (кому и когда его выдавать). Публичный релиз остаётся прежним, пока кандидат доступен только allowlist. В UI достаточно «Только выбранным установкам» → «Опубликовать всем совместимым установкам». Во время smoke полезны статусы «предложен», «скачан», «запущен», «проверен вручную»; последняя отметка не должна подменяться успешным HTTP 200.

Кандидат проверяется на той же production-сборке и с тем же runtime, на который пойдёт публичная раздача. Продвигать проверенные артефакты без повторной сборки JS. Identity и время публикации deployment должны учитываться отдельно: если публичный релиз уже стал новее кандидата, обычная раздача старого manifest может не переключить клиентов.

После promotion удалить/завершить override аудитории, иначе тестовый телефон может навсегда остаться закреплённым на старом кандидате. Рекомендуемое правило выбора: совместимость → активный разрешённый targeted deployment → публичный deployment → корректный no-update. Конфликтующие назначения одной установке должны иметь однозначный приоритет либо запрещаться.

Позже можно добавить процентный rollout со стабильным распределением по `hash(installationId, rolloutId)`. Это отдельная возможность: случайные 1% пользователей не гарантируют попадание именно вашего телефона. В EAS есть per-update процентная раздача, постепенное увеличение до 100% и процедуры отката. Это пример механики, а не готовая функция данного custom server. [EAS Rollouts](https://docs.expo.dev/eas-update/rollouts/).

## Ограничения протокола и откат

Протокол разрешает учитывать headers при выборе подходящего update. `204` без тела — допустимый no-op для multipart-протокола; обязательные protocol headers сохраняются. Manifest filters применяются к локальным update metadata, а server-defined headers сохраняются для следующих запросов. Персонализированный manifest нельзя случайно разделять через общий HTTP/CDN-cache; спецификация рекомендует `Cache-Control: private, max-age=0`. [Expo Updates v1](https://docs.expo.dev/technical-specs/expo-updates-1/).

Текущая Android selection policy в обычном случае принимает только update с более новым `commitTime`; исключения связаны с изменением filters, URL и configured request headers. Следовательно, простое удаление установки из allowlist или ответ «нет обновления» **не гарантирует возврат** со скачанного кандидата на более старую публичную версию. Не строить rollback на случайном поведении кеша или смене фильтров. [LoaderSelectionPolicyFilterAware.kt](https://github.com/expo/expo/blob/main/packages/expo-updates/android/src/main/java/expo/modules/updates/selectionpolicy/LoaderSelectionPolicyFilterAware.kt).

Для отката на прежний OTA Expo использует повторную публикацию прежнего содержимого; отдельно существует rollback-to-embedded. Поэтому проекту нужен явный rollback deployment с корректной identity/временем и совместимостью, а не только отключение кандидата. [Expo Rollbacks](https://docs.expo.dev/eas-update/rollbacks/).

OTA-аудитория похожа на feature flag способом выбора пользователей, но обновление применяется через скачивание и новый запуск JS. Нельзя гарантировать мгновенное удалённое переключение закрытого/offline приложения. Если нужен мгновенный on/off поведения уже установленного кода — это отдельный feature flag внутри приложения.

- Уточнить Expo SDK и `expo-updates` во всех обслуживаемых мобильных приложениях; проверить extra params на настоящих iOS/Android release-сборках.
- Проверить отсутствие installation ID, неверный ID, другую платформу/runtime, обычную публичную установку и выбранный телефон.
- Проверить переход public A → targeted B → public B/C, удаление allowlist, offline cold start и явный rollback.

- Проверить дубли, задержанные offline-события, embedded launch, reinstall, аварийный fallback и недоступную аналитику. Ошибка аналитики не должна блокировать запуск приложения.

### Особенность ID, которую нужно устранить до расчёта adoption

В текущем коде возможен следующий путь:

1. Работает OTA A. Publisher загружает неактивный B и меняет `latest_update_id` на B.
2. Триггер меняет ID manifest канала на X. Пока B неактивен, manifest-controller выбирает fallback A и может записать X → A.
3. Активация B оставляет `latest_update_id=B` и `active_update_id=null`. Триггер реагирует только на изменение этих указателей, поэтому X может остаться прежним.
4. У клиента на A с ID X проверка `currentUpdateId === id` может вернуть no-update. Для другого запроса запись X → B может перезаписать старое соответствие.

Это вывод по пути исполнения, а не воспроизведённый на устройстве дефект. Источники: [publisher](../../templates/expo-app/scripts/ota-publish/api/database-client.mjs), `ota_channels_rotate_served_manifest_id` в [схеме](../migrations/schema.sql), `recalculateChannelPointers`/`setUpdateDisabledByKey` в [admin-updates.ts](../../src/server/lib/admin-updates.ts), `matchesCurrentUpdate` в [manifest.ts](../../src/server/controllers/manifest.ts).

Для новой модели обязательный инвариант: один manifest UUID всегда обозначает один неизменяемый артефакт. Нельзя просто подставлять разные OTA для разных устройств под общим ID канала. Соответствие ID нужно сохранять надёжно до выдачи manifest, а не рассчитывать на необязательный фоновый upsert.

## Предлагаемая реализация для этого проекта

Ниже — рекомендации по проектированию, а не описание уже существующего поведения.

### 1. Статистика фактически запущенных версий

Основная сущность — **установка приложения**, не человек и не аппаратный телефон. Для количества людей понадобится отдельная связь с авторизованным user ID и согласованное правило дедупликации. Для смоук-теста достаточно installation ID с подписью «мой iPhone».

Расширить `ota_device_state`:

- стабильный installation ID, platform, channel и runtime;
- нативные app version и build number;
- сырой ID текущего запуска, разрешённый OTA artifact ID, признак embedded и известный embedded ID;
- время последнего подтверждённого запуска/активности; отдельно время последней проверки OTA;
- источник наблюдения и состояние `known OTA / embedded / unknown`;
- признак emergency launch, чтобы видеть возможный возврат к запасной версии.

Нативную версию получать из `Application.nativeApplicationVersion`, номер сборки — из `Application.nativeBuildVersion`. Значение версии из загруженного OTA manifest не заменяет версию установленного бинарника. [Expo Application](https://docs.expo.dev/versions/latest/sdk/application/).

Добавить клиентский heartbeat: после запуска приложения и при возврате в foreground с ограничением частоты отправлять текущие данные запуска. После reload новый JS должен сообщить новый update ID. Проверка manifest может дополнять наблюдения, но не должна превращать выбранное/скачанное обновление в «запущенное».

Предлагаемые интерфейсы: `POST /api/device-heartbeat`, `GET /api/admin/devices`, `GET /api/admin/analytics/versions`. Это новые маршруты, их сейчас нет. Старый `update-complete` можно постепенно заменить этим контрактом, сохранив совместимость старых клиентов.

Для доставки событий предусмотреть event ID, повторную отправку, порядок событий и защиту от старого offline-события, перезаписывающего более новое состояние. Обновление state и вставку transition выполнять атомарно. Heartbeat не должен блокировать запуск приложения, но подтверждать приём сервер должен после надёжной записи либо постановки в очередь. Недоступность аналитики не должна останавливать OTA.

В отчёте показывать:

| Разрез | Зачем нужен |
| --- | --- |
| Нативная версия + build + runtime | Какие бинарники ещё используются и требуют поддержки |
| OTA artifact ID + понятная подпись релиза | Какая JS-версия реально работает |
| Platform/channel | Не смешивать разные аудитории и совместимость |
| Активные установки за 24 часа / 7 / 30 дней | Не считать давно исчезнувшие установки текущей аудиторией |
| Доля от наблюдаемых активных установок выбранного scope | Понятный знаменатель adoption |
| Embedded / unknown / давно не выходили на связь | Не выдавать неполные данные за точное распределение |
| Offered / downloaded / launched / healthy, если эти события реализованы | Отделить доступность и доставку от успешной работы |

`healthy` — отдельное прикладное подтверждение, например после загрузки основного экрана; сам факт запуска JS ещё не доказывает успешный смоук-тест. Если нужна динамика по дням, нужны дневные агрегаты/события активности: одной строки последнего состояния недостаточно для восстановления прошлого распределения.

Начальная статистика будет покрывать только клиентов с телеметрией. Сначала доставить инструментирование в поддерживаемые runtimes, затем накопить данные; старые приложения без него не станут наблюдаемыми автоматически.

При удалении OTA нынешняя схема удаляет mapping через cascade и обнуляет `current_update_id`. Для долгосрочной аналитики сохранять архивные метаданные релиза/сырой ID независимо от наличия assets; предпочтительнее архивирование артефакта вместо уничтожения его истории. Источники: [схема](../migrations/schema.sql), [deleteUpdateByKey](../../src/server/lib/admin-updates.ts).

### 2. Адресный выпуск: артефакт отдельно, аудитория отдельно

Рекомендуемая отдельная сущность `ota_deployments`: конкретный artifact, scope, состояние, аудитория `selected installations | everyone`, собственные manifest UUID/createdAt, версия настройки и журнал изменений. Список адресатов — отдельная таблица `ota_deployment_installations`.

Для первой версии достаточно одного тестового deployment на scope и списка installation ID. Проценты, сегменты и сложный feature-flag engine для данного кейса не нужны. Позже можно добавить стабильное распределение по хешу installation ID + rollout seed.

Разделение обязанностей:

- **Artifact:** неизменяемый экспорт JavaScript/assets.
- **Deployment/audience:** кому этот артефакт разрешено предложить.
- **Delivery policy:** когда клиент скачивает и применяет разрешённый OTA.
- **Installation state:** что клиент подтвердил как реально запущенное.

В MVP возможно сохранить `is_active` как маркер публичного OTA, а ограниченную выдачу разрешать только через опубликованный targeted deployment. Тогда существующий уникальный индекс продолжает защищать публичную ветку. Это требует отдельного явного пути выбора: текущая проверка `is_active` отвергает тестовый артефакт. Более полный вариант — перенести всю активацию на deployment. Просто удалить уникальный индекс или сделать тестовый OTA глобально активным недостаточно.

При ограниченной публикации нужно заморозить policy артефакта так же, как при публичной: уже отданный тестеру manifest должен оставаться воспроизводимым. Существующий `policy_published_at` помогает, но все способы изменения опубликованного артефакта следует согласовать. [Контракт policy](../ota-update-policy.md), [схема](../migrations/schema.sql).

Порядок разрешения запроса:

1. Глобальная остановка выдачи имеет высший приоритет.
2. Проверить platform/runtime/channel и применить существующее emergency recovery; для MVP отключать обычный тестовый override при срабатывании emergency-правила.
3. Найти подходящий deployment для данной установки внутри разрешённого scope.
4. Для остальных выбрать публичное стабильное OTA. Не возвращать всем no-update только потому, что тестовая версия им не положена.
5. Применить защиты совместимости, downgrade/no-update, подпись и сформировать manifest выбранного deployment.

Отсутствующий/некорректный installation ID означает только публичную ветку. Конфликт двух адресных назначений одной установке лучше отклонять при настройке, чем разрешать случайным порядком строк. Нужно повторно проверить адресность на fetch-запросе: решение между check и download может измениться.

Публикация и promotion должны атомарно менять аудиторию/указатели и надёжно сохранять ID mapping. Новые записи deployment должны использовать существующую блокировку distribution control и её DB-защиту, чтобы targeted-выпуск не обходил аварийный выключатель. [distribution-control.ts](../../src/server/lib/distribution-control.ts), [схема](../migrations/schema.sql).

Нельзя привязывать новые записи только к текущему `latest_update_id`: он меняется уже при загрузке черновика. Promotion должен открывать всем **конкретный проверенный artifact**, даже если после него загрузили другой черновик. Для проверявшего устройства повторное скачивание того же артефакта обычно не нужно; сравнение должно учитывать нормализованный artifact ID.

### 3. Пользовательский сценарий

1. В приложении открыть диагностический экран, скопировать installation ID.
2. В админке найти установку и назвать её «мой iPhone».
3. Загрузить OTA B; для остальных продолжает работать стабильное A.
4. Выбрать «Только выбранные устройства» и назначить B своему installation ID.
5. На телефоне проверить, скачать, применить OTA; админка получает подтверждение запуска B.
6. Провести смоук-тест.
7. Нажать «Открыть всем»: тот же артефакт B становится публичным для совместимых клиентов этого scope.
8. При неудаче остановить дальнейшую выдачу B и при необходимости отдельно выполнить rollback тестовой аудитории.

«Всем» здесь означает подходящие platform/runtime/channel, а не любой установленный бинарник. Выпуск на обе платформы потребует соответствующих артефактов для iOS и Android.

Снятие устройства из списка останавливает будущую выдачу. Уже скачанный OTA может запуститься из кеша, а запущенный продолжит работу. Для фактического отката требуется отдельный совместимый recovery deployment; если приложение offline, сервер не может немедленно изменить его состояние.

### 4. Граница адресности и доступа

Для обычного внутреннего смоук-теста UUID установки подходит как ключ аудитории. Он не доказывает личность устройства. Если «только мне» также означает запрет посторонним скачать тестовый bundle, нужен проверяемый credential регистрации устройства, проверка выдачи assets и исключение публичного обходного URL.

Сейчас [assets.ts](../../src/server/controllers/assets.ts) проверяет глобальную блокировку и принадлежность asset указанному обновлению, но не installation ID/аудиторию. Поэтому manifest-targeting сам по себе даёт управление распространением среди штатных клиентов, а не закрытый доступ к файлам. Admin/publisher access tokens нельзя переносить в мобильное приложение.

Персональные manifest-ответы нельзя кешировать общим CDN-ключом. Текущий ответ имеет `private, max-age=0`; для адресной выдачи рекомендуется `private, no-store` и проверка фактических proxy/CDN-настроек. [manifest-response.ts](../../src/server/manifest/manifest-response.ts).

### 5. Как решать, какие версии поддерживать

На первом этапе принимать решения по наблюдаемым активным установкам за 30 дней, дополнительно смотреть 7 дней, unknown/embedded и покрытие телеметрии. Конкретный порог прекращения поддержки — продуктовая договорённость; по одному проценту OTA adoption нельзя автоматически выключать старый API или удалять assets.

Для OTA внутри совместимого runtime клиент обычно может сразу получить целевую версию. Если релиз содержит прикладные миграции данных, их способность пропускать промежуточные версии нужно проверить отдельно.

Переход на несовместимый runtime требует установки нового бинарника из магазина/другого канала распространения: OTA не заменяет нативные библиотеки. [Expo runtime versions](https://docs.expo.dev/eas-update/runtime-versions/).

Текущий `ota-force-store-update` — имя client guard. Сервер лишь передаёт его в manifest предложенного совместимого OTA; клиент должен реализовать обработку. Если нового совместимого OTA нет или ответ no-update, этот механизм не обеспечивает самостоятельную проверку минимальной поддерживаемой версии. Для такой задачи рекомендуется отдельный support-policy endpoint/config, проверяемый приложением независимо от OTA-кандидата. [ota-update-policy.md](../ota-update-policy.md), [manifest.ts](../../src/server/controllers/manifest.ts).

## Порядок работ и критерии проверки

1. Исправить/зафиксировать неизменяемое соответствие manifest ID и артефакта, затем внедрить клиентскую идентификацию, heartbeat и отчёт версий.
2. Добавить ограниченный deployment, выбор аудитории и UI «выбранные устройства / все», сохранив стабильную публичную выдачу.
3. Добавить promotion именно проверенного артефакта и отдельный rollback тестовой аудитории.
4. После накопления данных — правила поддержки runtime, при необходимости проценты rollout.

До реализации проверить версии Expo SDK/expo-updates в реальном мобильном проекте. Здесь находятся сервер и шаблоны, но нет доказательства версии клиентской native-библиотеки. Если нужного native API или модуля хранения/идентификации нет в установленном бинарнике, потребуется новый native build.

Будущая проверка должна включать две реальные release-установки одинакового scope: одна в аудитории получает B, другая получает A; после promotion вторая получает тот же артефакт B. Дополнительно: missing ID; другой runtime/platform; повторный heartbeat; задержанные offline-события; embedded/unknown; остановка выдачи; rollback уже скачанного B; публикация нового черновика до promotion; сохранность mapping при fallback/активации; одинаковое поведение PG и Supabase.

В рамках этого исследования продуктовый код и миграции не менялись; перечисленные сценарии — критерии будущей реализации, а не выполненные проверки.

## Реализация подготовительного кандидата — 2026-10-16

Кандидат выбран до heartbeat, поскольку статистика зависит от достоверного разрешения ID. Два независимых ревью проверили доставку/совместимость и изменения БД. По результатам ревью одного нового UUID оказалось недостаточно: дата публикации также должна строго возрастать, чтобы Expo принимал следующую OTA.

Решение: UUID v5 от epoch канала и выбранного update ID; обязательная запись mapping до ответа; SQL-защита от переназначения mapping; ротация epoch и продвижение даты при активации и смене rollback-состояния. Удалены предварительные записи сырых epoch ID из админки. Старые mappings сохранены. Это защита соответствия ID, а не запрет любых изменений содержимого опубликованного артефакта.

Регрессионный тест воспроизвёл ошибочный no-update после активации черновика до исправления. Добавлены проверки повторных запросов, холодного запуска сервера, ожидания записи и её отказа, а также совместимости с историческими ID. SQL-сценарии находятся в [manifest-identity.sql](../../scripts/tests/manifest-identity.sql); миграция — [2026-10-16-manifest-identity.sql](../migrations/2026-10-16-manifest-identity.sql). Проверка на физических устройствах и внедрение в рабочую БД выполняются отдельно.

Итоговая проверка: 212 тестов Vitest, TypeScript, production build Next.js и сборка документации прошли. ESLint изменённых файлов прошёл; полный lint сообщает одно прежнее предупреждение в embedded-registration plugin. SQL проверен через временную PGlite вне зависимостей проекта: чистая схема и обновление схемы исходного HEAD, повторное применение миграции, сохранность существующей legacy-записи, сценарии триггеров. В этой среде исключалась только недоступная команда установки pgcrypto; используемый gen_random_uuid доступен встроенно. Docker daemon был недоступен, поэтому проверка конкуренции на двух независимых PostgreSQL-соединениях не проводилась. Повторное независимое ревью реализации не выявило блокирующих замечаний.
