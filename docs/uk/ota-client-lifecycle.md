# Життєвий цикл згенерованого OTA-клієнта {#generated-ota-client-lifecycle}

`configure-app` генерує відформатований TypeScript-клієнт і розміщує `<OtaUpdates />` поруч із навігацією в кореневому layout/App. Компонент викликає `useOtaUpdates` усередині; він не обгортає застосунок і не надає React-контексту. Монтуйте його один раз у постійному корені, включно з гілками завантаження та раннього повернення.

За замовчуванням він автоматично перевіряє оновлення й пропонує **Download / Later** для звичайного оновлення, а після завантаження — **Restart / Later**. `autoUpdate={false}` вимикає автоматичне завантаження, але не пропозицію. Відхилений кандидат прихований до повторного монтування, появи іншого кандидата або зміни стану завантаження. Фонові оновлення залишаються непомітними; обов’язкові не можна відхилити.

Низькорівневий `useOtaUpdates()` доступний для необов’язкових власних екранів. Він поділяє стан і дії, але за замовчуванням не автоматизує їх і не виводить інтерфейсу. Налаштовуйте автоматизацію в одному корені; кілька налаштованих споживачів об’єднують логічні параметри через OR. Зберігайте стабільність власних обробників Guard.

Ідентифікатори зберігаються та встановлюються в параметри запитів Expo до будь-якої перевірки або завантаження. Сигнали запуску й повернення на передній план повідомляють лише **запущений** пакет, а не завантаженого кандидата. Мережева телеметрія не блокує запуск або перевірку оновлень. У режимі розробки, Expo Go, web і збірках із вимкненими оновленнями автоматизацію вимкнено.

| Політика/параметри | Поведінка |
| --- | --- |
| manual, стандартні параметри | OtaUpdates пропонує завантаження/перезапуск; один хук надає стан |
| autoCheck | Перевірка під час монтування та виходу на передній план, мінімальний інтервал 60 секунд |
| autoUpdate | Також завантажує придатних кандидатів із ручною доставкою |
| autoReload | Перезапускає нефоновий пакет, що очікує, коли застосунок активний |
| delivery=background | Непомітно завантажує; застосовує під час наступного холодного запуску або ручного перезапуску |
| guard=ota-force-update | Блокує екраном, автоматично завантажує; після готовності показує кнопку перезапуску |
| guard=ota-force-store-update | Блокує екраном; відкриває магазин, ніколи не завантажує цього кандидата |
| власний/невідомий Guard | Блокує, доки guardHandlers[action] явно не поверне `allow` |

Дані Guard магазину: `{ "androidUrl": "market://details?id=com.example.app", "iosUrl": "https://apps.apple.com/app/id123" }`; `url` — спільний резервний варіант. Допускаються лише URL https, market та itms-apps. Нативне оновлення, як і раніше, вимагає релізу в магазині; OTA не може додати нативні модулі або змінити встановлений runtime.

Вбудований блокувальний екран — модальне вікно, яке неможливо закрити й яке зберігає змонтовану навігацію та провайдери. Налаштуйте обов’язковий інтерфейс через `renderBlocked`, необов’язковий — через `renderAvailable`. Залишайте `OtaUpdates` поруч із навігацією; один хук надає `blocked`, але не запобігає взаємодії з вашими екранами. Невідомі Guard закривають доступ. Обов’язкові перевірки — мережева політика, а не автентифікація чи захист від втручання. Помилка перевірки без мережі залишає застосунок доступним, якщо обов’язкового кандидата ще не виявлено й запущений пакет не вимагає Guard магазину або власного Guard.

Одночасно виконується один виклик кожної дії; інша дія під час зайнятості відхиляється. Помилки доступні в `error`, повернені Promise відхиляються, тому ручні виклики обробляйте через try/catch. Повторна спроба знову перевіряє сервер і переоцінює власний Guard кандидата, що очікує. Завантаження повторно оцінює політику отриманого маніфесту: вона може відрізнятися від перевіреного кандидата. Пакет, що очікує, керує блокувальним екраном до перезапуску; перевірка іншого кандидата не дозволяє старий кешований пакет. Підтримуються нативні директиви відкату. Expo керує завантаженням уже отриманих пакетів під час холодного старту; JS Guard не може відкликати цей нативний кеш. Guard магазину та власні Guard повторно перевіряються за запущеним маніфестом на наступному запуску; вимога примусового OTA вже виконана запуском цього пакета. Не змішуйте прямі виклики expo-updates або нативні автоматичні перевірки з керуванням хуком: configure-app використовує checkAutomatically=NEVER.

Старі експорти `checkForUpdateAsync`/`fetchUpdateAsync` залишаються низькорівневими API з урахуванням ідентифікаторів для наявних інтеграцій. Вони навмисно не реалізують політики хука. Облікові дані БД або адмінки до застосунку не потрапляють: сервер зберігає публічні сигнали активності.

## Підключення та налаштування {#integration-and-customization}

Виконайте стандартну `npm run configure-app -- ...` із проєкту сервера. Вона зберігає початкову точку входу, генерує клієнт і вставляє самостійний компонент до підтримуваних кореневих компонентів. Для Expo Router це `src/app/_layout` (пріоритетний за наявності `src/app`) або `app/_layout`, включно з платформними варіантами. Для стандартної точки входу — `App`, якщо власний `index` не реєструє інший корінь. Синхронні функціональні компоненти та підтримувані форми експорту за замовчуванням змінюються без зміни навігації. Непідтримувана форма кореня відхиляється до запису; невизначуваний власний корінь зберігає автоматичні ідентифікацію/телеметрію та отримує попередження про ручне підключення життєвого циклу. Згенероване підключення починається з:

```tsx
return (
  <>
    <OtaUpdates autoCheck autoUpdate={false} autoReload={false} />
    <AppTabs />
  </>
);
```

Змінюйте ці параметри в кореневому компоненті. На інших екранах використовуйте `useOtaUpdates()` для ручного керування та спільного стану. Конфігуратор вибирає відповідний шлях імпорту; облікові дані БД і адмінки не мають потрапляти до застосунку. Згенерований код включає `ota-client/docs/update-lifecycle.md` із цим контрактом для розробників застосунку.

Для вже налаштованого проєкту перевірте зміни згенерованих файлів і повторіть із `--force`. Це замінює старі JavaScript-файли на TypeScript, видаляє застарілі копії `.js`/`.d.ts`, здатні перекривати нові модулі, та переносить стандартний кореневий хук/екран зі збереженням параметрів. Код зі старим кореневим контролером або власним блокувальним екраном переноситься вручну; попередня перевірка зупиняє процес до будь-яких записів. Використовуйте `.tsx` для коренів TypeScript JSX. Наявні споживачі `OtaUpdateGate` підтримуються. Нативні залежності вимагають нової збірки; використовуйте новий runtime, якщо старі встановлені збірки не мають цих модулів. Публікація залишається через згенеровану `npm run ota:publish`. Див. [вибір пристроїв](./device-targeting.md) для smoke-аудиторії та [телеметрію встановлень](./installation-telemetry.md) для правил отримання подій і аналітики.

## Ручне підключення {#manual-integration}

Використовуйте цей шлях, якщо `configure-app` не може змінити кореневий компонент, проєкт використовує динамічний `app.config.*` або ви хочете підключити клієнт самостійно. Хук — вихідний код із цього репозиторію, **а не npm-пакет**. Не імпортуйте його з `expo-updates`.

### 1. Підготуйте клієнт і нативну конфігурацію {#_1-prepare-the-client-and-native-configuration}

Якщо після налаштування вже є `ota-client/index.ts`, `ota-client/types.ts` і `ota-client/config.json`, збережіть їх і переходьте до кроку 2. Попередження про невизначуваний власний корінь означає, що початкове завантаження та клієнт встановлені; помилка непідтримуваного кореня зупиняє налаштування до запису, тому перевірте реальні файли.

Для застосунку без згенерованого клієнта виконайте з каталогу застосунку:

```bash
npx expo install expo-updates expo-application expo-crypto expo-secure-store @react-native-async-storage/async-storage
```

Скопіюйте **весь** каталог `templates/expo-app/ota-client/` із репозиторію OTA-сервера до `<application>/ota-client/`. Збережіть разом вкладені `model/`, `ui/`, файли виконання, ідентифікації, телеметрії та типів. Наприклад, якщо такого каталогу в застосунку ще немає:

```bash
cp -R /full/path/to/expo-updates-server/templates/expo-app/ota-client ./ota-client
```

Створіть `<application>/ota-client/config.json`:

```json
{
  "channel": "preview",
  "heartbeatUrl": "https://updates.example.com/api/device-heartbeat",
  "identityNamespace": "https://updates.example.com"
}
```

Використовуйте реальний URL сервера. `channel` має збігатися з нативним заголовком запиту `expo-channel-name`. `identityNamespace` — стабільна область ідентифікації: зберігайте наявне значення під час зміни тунелю/домену, runtime або каналу. Секрету тут немає. Не копіюйте до файла ID встановлення, ID пристрою, пароль БД або токен адмінки: клієнт сам створює ідентифікатори й надсилає публічні сигнали активності.

Завершіть [нативну конфігурацію Expo](./expo-app-setup.md#_3-configure-the-expo-application): URL маніфесту сервера, відповідний публічний сертифікат, runtime і канал. Задайте `updates.checkAutomatically` як `NEVER`; перевірки мають чекати налаштування ідентифікаторів. Зберігайте приватний ключ підпису й дані публікатора поза мобільним пакетом. Динамічна конфігурація має обчислювати той самий канал, що в `ota-client/config.json`.

### 2. Підключіть кореневий layout або App {#_2-connect-the-root-layout-or-app}

Для Expo Router розмістіть компонент поруч із навігацією в наявному `src/app/_layout.tsx`. Збережіть провайдери, шрифти, обробку заставки та інший код layout. Не розміщуйте компонент у колекціях дочірніх елементів лише для навігатора, таких як `Stack.Screen`/`Tabs.Screen`.

```tsx
import { Stack } from 'expo-router';
import { OtaUpdates } from '../../ota-client';

export default function RootLayout() {
  return (
    <>
      <OtaUpdates autoCheck autoUpdate={false} autoReload={false} />
      <Stack />
    </>
  );
}
```

Скоригуйте відносний імпорт за розташуванням файла:

| Кореневий файл | Шлях імпорту |
| --- | --- |
| `src/app/_layout.tsx` | `../../ota-client` |
| `app/_layout.tsx` | `../ota-client` |
| `App.tsx` у корені застосунку | `./ota-client` |

Для застосунку без Router розмістіть той самий компонент поруч із наявним вмістом. Він може бути сусідом класового компонента. Монтуйте один екземпляр, включно із завантаженням і ранніми поверненнями. Власна точка входу, як і раніше, реєструє початковий корінь.

Збережіть наявний згенерований `ota-entry.js` і його налаштування `package.json.main`. За повністю ручного підключення змінювати точку входу **не потрібно**: змонтований хук сам викликає ідемпотентний `start()` телеметрії. Ідентифікатори зберігаються до запитів оновлення; мережеві помилки сигналів активності не блокують відображення та перевірки. Не додавайте іншу реалізацію телеметрії й не викликайте перевірки Expo під час ініціалізації модуля. Якщо реєстрація потрібна до монтування кореня, публічний `start()` також можна викликати в наявній точці входу, не замінюючи початковий код реєстрації.

`OtaUpdates` надає стандартний інтерфейс примусового оновлення. Якщо використовується лише хук, потрібен власний інтерфейс, який застосовує `blocked`. Власний блокувальний екран підтримується через `renderBlocked`; це не змінює рішення Guard контролера.

### 3. Додайте ручне керування оновленнями {#_3-add-manual-update-controls}

Корінь уже надає елементи завантаження/перезапуску. Окремий екран налаштувань необов’язковий і може підписатися без увімкнення ще одного автоматичного процесу. Наприклад, `src/components/ota-controls.tsx`:

```tsx
import { useState } from 'react';
import { Button, Text, View } from 'react-native';
import { useOtaUpdates } from '../../ota-client';

export function OtaControls() {
  const ota = useOtaUpdates();
  const [message, setMessage] = useState('');

  async function perform(action: () => Promise<unknown>) {
    try {
      setMessage('');
      await action();
    } catch (error) {
      setMessage(error instanceof Error ? error.message : String(error));
    }
  }

  return (
    <View>
      <Text>Installation: {ota.installationId ?? 'Initializing'}</Text>
      <Text>Device: {ota.deviceId ?? 'Unavailable'}</Text>
      <Text>State: {ota.status}</Text>
      <Text accessibilityLiveRegion="polite">{message || ota.error?.message}</Text>
      <Button title="Check OTA" disabled={!ota.enabled || ota.isBusy}
        onPress={() => { void perform(ota.check); }} />
      <Button title="Download OTA"
        disabled={!ota.enabled || ota.isBusy || !ota.available || ota.pending || ota.blocked}
        onPress={() => { void perform(ota.download); }} />
      <Button title="Restart with OTA"
        disabled={!ota.enabled || ota.isBusy || !ota.pending || ota.blocked}
        onPress={() => { void perform(ota.reload); }} />
    </View>
  );
}
```

Блокувальний екран надає дії обов’язкового оновлення, поки звичайні екранні елементи заблоковані. Для автоматичного завантаження звичайних оновлень задайте `autoUpdate: true` у корені; додавайте `autoReload: true`, лише якщо застосунку підходять автоматичні перезапуски на передньому плані. Серверна доставка `background`, як і раніше, забороняє негайний автоматичний перезапуск. Власні Guard потребують явного рішення `guardHandlers[action]`; повернення `allow` має відповідати реальній умові застосунку, а не просто приховувати невідому дію.

### 4. Перезберіть і перевірте {#_4-rebuild-and-verify}

Після додавання нативних залежностей або зміни URL/runtime/каналу/сертифіката виконайте prebuild і встановіть нову релізну збірку. Використовуйте оточення, потрібне динамічній конфігурації, під час запуску команд Expo. Expo Go і звичайний режим розробки не перевіряють життєвий цикл телеметрії/оновлень цього клієнта.

1. Перевірте TypeScript і lint, потім зберіть та встановіть реліз.
2. Запустіть його й переконайтеся, що встановлення з’явилося в `/updates/devices`.
3. Опублікуйте нове OTA **після** збірки нативного застосунку для його точної області, потім активуйте.
4. Перевірте → завантажте → перезапустіть; підтвердьте нову запущену версію в адмінці.
5. Переконайтеся, що ID встановлення не змінився після OTA. Перевстановлення може змінити його; збереження ID пристрою має [платформні обмеження](./device-targeting.md).
6. Окремо перевірте фонову доставку, примусове OTA, оновлення з магазину та власні Guard.

Копіювання `ota-client/` і додавання хука не встановлюють скриптів публікатора та реєстрації вбудованих збірок. Це окремі кроки [посібника із застосунку](./expo-app-setup.md#_6-register-embedded-updates). Якщо автоматичний конфігуратор уже їх встановив, продовжуйте використовувати його `npm run ota:publish`. Вбудований публікатор читає лише статичний `app.json`: ручне підключення хука не робить проєкт із динамічним `app.config.*` підтримуваним наскрізним процесом публікації. Таким проєктам потрібна окрема інтеграція публікації та збірки до кроку 3 вище.
