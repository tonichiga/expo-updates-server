# Діагностика налаштування з doctor {#diagnose-setup-with-doctor}

Запускайте `doctor` з **каталогу сервера**. Він перевіряє сервер і, за потреби, застосунок Expo, не змінюючи файли, не запускаючи контейнери, не застосовуючи міграції, не завантажуючи ресурси й не активуючи оновлення. Рекомендовано Node.js 24; парсер env вимагає Node.js 20.12+. Для перевірки призначення сертифіката також потрібен виконуваний файл OpenSSL.

```bash
npm ci
npm run doctor -- --app ../my-expo-app
```

За замовчуванням використовується **режим Docker** з `.env` і `docker-compose.yml`. Сервіс `app` має працювати. Перевірки БД, бакета та ключа підпису виконуються всередині контейнера від його звичайного користувача, тому перевіряють реальний доступ контейнера, а не права хоста на читання підключеного ключа.

Щоб до запуску перевірити лише файли сервера:

```bash
npm run doctor -- --offline --certificate ./local-certificates/code-signing-certificate.pem
```

Автономні перевірки Docker використовують зіставлення env стандартного шаблону та шлях ключа на хості `secrets/code-signing-private-key.pem`. Вони не обчислюють власні перевизначення Compose і не доводять, що контейнер може прочитати ключ.

## Віддалене розгортання або запуск через npm {#remote-or-npm-deployment}

Виберіть віддалений режим явно. Він читає **лише** вибраний env-файл, не домішуючи облікові дані оболонки й не завантажуючи неявно інший `.env.local`:

```bash
npm run doctor -- \
  --mode remote \
  --server-env ./server.env \
  --app ../my-expo-app
```

Режим підтримує конфігурації PostgreSQL/S3 і Supabase. Запускайте його там, де доступні env-файл, приватний ключ, БД і сховище. Відносні шляхи до приватного ключа відлічуються від каталогу сервера. Ім’я хоста не означає SSH-підключення або доступ до віддаленої файлової системи. Підстановка змінних env у віддаленому режимі не виконується; використовуйте явні значення. URL PostgreSQL має містити користувача, пароль і БД; із параметрів URL підтримується лише `sslmode`. Порт за замовчуванням явно дорівнює 5432, тому зовнішні змінні `PG*` не можуть непомітно вибрати інше підключення.

## Власний проєкт Docker {#custom-docker-project}

Передайте ті самі проєкт і файли Compose, які використовувалися під час запуску, у тому самому порядку:

```bash
npm run doctor -- \
  --server-env .env.ota-test \
  --project ota-test \
  --compose-file docker-compose.yml \
  --compose-file docker-compose.ota-test.yml \
  --app ../rn-app-ota-test
```

`--compose-file` можна повторювати. Ці тестові файли належать локальному стенду; для створеного проєкту використовуйте власні. Налаштування підключення й контексту Docker передаються, а довільні env-перевизначення застосунку з оболонки — ні. Мережева перевірка читає оточення запущеного застосунку й повідомляє про невідповідність публічного URL вибраному env-файлу.

## Що перевіряється {#what-is-checked}

| Область | Перевірки |
| --- | --- |
| Середовище виконання | Парсер env Node та залежності сервера |
| Оточення | Явний env-файл, значення-заглушки, особливості екранування Docker |
| Підпис | Читабельний RSA-ключ не коротший за 2048 біт, чинний публічний сертифікат не-CA, призначення Digital Signature / Code Signing, збіг публічних ключів |
| URL сервера | Коректний публічний URL, доступ хоста до `/api/health`, застереження щодо loopback та HTTP |
| PostgreSQL | Підключення, читання основних стовпців OTA/телеметрії/аудиторії, потрібні сигнатури таблиць і функцій, увімкнений тригер активації аудиторії |
| Supabase | Читання основних REST-таблиць, стовпців і бакета; тіла SQL-функцій не перевіряються |
| Сховище | Наявність і доступність бакета через S3 HEAD або Supabase bucket GET; без запису |
| Застосунок Expo | Статична конфігурація, встановлені клієнтські залежності, файли реалізації, URL/канал/runtime, нативний режим перевірки, простір ідентифікаторів і URL телеметрії |
| Корінь застосунку | Розпізнане підключення хука та блокувального екрана, згенеровані метадані початкового завантаження; власні корені потребують ручної перевірки |
| Публікатор/реєстратор | Наявність і базова структура облікових даних `.env.ota`, команда публікації, узгодженість каналу та URL реєстрації |

Без `--app` перевірки застосунку пропускаються. Без сертифіката застосунку або явного `--certificate` порівняння пари ключів пропускається. Явний сертифікат має пріоритет над сертифікатом застосунку; якщо це інший файл, виводиться попередження. Doctor ніколи не виконує `app.config.*`; для таких проєктів повідомляє про обмеження статичною конфігурацією.

Кожна перевірка повертає `pass`, `fail`, `warn` або `skip`, а за потреби — конкретний спосіб виправлення. Необроблені винятки, облікові дані, приватні ключі та рядки підключення до виводу не включаються.

## CI і тайм-аути {#ci-and-timeouts}

```bash
npm run --silent doctor -- --mode remote --server-env ./server.env --json
```

Використовуйте `--silent`, щоб npm не додавав заголовок команди перед JSON. Вивід має версіоновану структуру:

```json
{
  "version": 1,
  "mode": "remote",
  "offline": false,
  "status": "fail",
  "checks": [
    {
      "id": "signing.key",
      "status": "fail",
      "message": "Signing key is missing, unreadable or invalid.",
      "remedy": "Check the signing key configuration and read permissions."
    }
  ]
}
```

Коди завершення: `0` — блокувальних проблем не виявлено (можуть залишитися попередження та пропуски), `1` — перевірки не пройдено, `2` — неправильні аргументи або неочікувана помилка діагностики. `--timeout 10000` дозволяє 10 секунд на мережеву операцію; підтримується 500–30000 мс. Деякі перевірки послідовні, тому сумарний час може перевищувати один тайм-аут. Виконання Docker також обмежене загальним часом.

## Чого успішна перевірка не доводить {#what-a-pass-does-not-prove}

Doctor не перевіряє нативні SDK та інструменти, не виконує збірки, не порівнює всі визначення міграцій і не перевіряє права запису. Наявність токена не доводить його дозволи. Облікові дані застосунку можуть відрізнятися від серверних; авторизацію публікатора й реєстратора потрібно перевірити реальною збіркою та публікацією. Налаштування контейнера, крім публічного URL, перевіряються в поточному стані, а не вичерпно порівнюються з майбутніми змінами Compose.

Доступність URL із хоста не доводить доступність із телефона. Конфігурація вихідного коду також не доводить, які URL/runtime/сертифікат встановлені в нативній збірці. Після виправлення виконайте [швидкий старт](./getting-started.md) або [перевірку на новому застосунку](./expo-app-setup.md#verify-generation-in-a-fresh-application): збірка → встановлення → публікація → активація → завантаження → перезапуск.
