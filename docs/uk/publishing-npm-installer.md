# Публікація `create-expo-updates-server` {#publishing-create-expo-updates-server}

Кореневий пакет Next.js залишається закритим. Публікується лише робочий пакет `packages/create-expo-updates-server`.

## Одноразове налаштування npm {#one-time-npm-configuration}

До будь-якої публікації захистіть оточення GitHub `npm-publish`, призначивши обов’язкових рецензентів релізу. Звичайні релізи використовують npm Trusted Publishing і workflow `.github/workflows/publish-create-expo-updates-server.yml` лише з OIDC; npm-токен не використовується.

### Перша публікація {#first-publication}

Спочатку спробуйте налаштувати npm **Trusted Publisher** для `tonichiga/expo-updates-server`, workflow `.github/workflows/publish-create-expo-updates-server.yml` та оточення `npm-publish`.

Якщо npm вимагає наявності пакета для такого налаштування, уповноважений супроводжувач може виконати рівно одну ручну публікацію:

1. Виконайте перевірки релізу нижче, потім зберіть один архів командою `npm pack --workspace create-expo-updates-server`. Перевірте `.tgz` і збережіть перевірений файл без повторної збірки.
2. На довіреному комп’ютері супроводжувача увійдіть до npm з одноразовим кодом OTP і виконайте `npm publish <reviewed-tarball> --access public`. Не додавайте `--provenance`: перша ручна публікація не матиме підтвердження походження від GitHub.
3. Одразу налаштуйте Trusted Publisher, описаний вище.

Ніколи не зберігайте токен публікації npm у GitHub, репозиторії, workflow або файлі супроводжувача. Початкового workflow з токеном немає. Усі наступні публікації мають використовувати Trusted Publishing за тегом.

## Процедура релізу {#release-procedure}

1. Створіть гілку від актуального `main`.
2. Збільште `version` у `packages/create-expo-updates-server/package.json` і виконайте `npm install`, щоб кореневий lock-файл зафіксував точно таку саму версію робочого пакета.
3. Виконайте:

   ```bash
   npm ci
   npm run installer:check
   npm run installer:pack-smoke -- --docker
   npm run docs:build
   ```

   Потрібні доступні Docker Engine і Compose 2.24.4+. Smoke-тест із `--docker` запускає проєкт, створений з упакованого npm-артефакту, з новими томами, тимчасовими обліковими даними та ключами, а також випадковими loopback-портами. Він перевіряє стан БД, доступ до ключа підпису, завантаження й отримання ресурсів, повторювану ініціалізацію бакета, потім видаляє лише власні контейнери й томи. Перша збірка MinIO з вихідного коду займає кілька хвилин. Без `--docker` перевіряються лише створення проєкту та встановлення залежностей.

4. Відкрийте pull request і об’єднайте його лише після успішних CI та рев’ю.
5. На об’єднаному коміті створіть і надішліть тег саме такого вигляду:

   ```text
   create-expo-updates-server-v<version>
   ```

   Наприклад, для версії пакета `0.2.0` потрібен тег `create-expo-updates-server-v0.2.0`.

Workflow, що запускається лише за тегом, звіряє тег із версією пакета, повторно збирає й тестує детермінований шаблон і перевіряє, що позначений коміт є предком `origin/main`. Перевірка виконується до входу в захищене оточення `npm-publish`. Створюється один архів релізу; саме цей артефакт передається завданню публікації із захистом оточенням і публікується з публічним доступом та npm provenance через OIDC. Невідповідність тега, не включений до main коміт або невідповідність SHA робочої копії та події блокують публікацію.

Завдання публікації має лише `contents: read` та `id-token: write`; доступ до npm забезпечує Trusted Publishing. Не розширюйте дозволи й не переносіть кроки збірки до завдання із захищеним оточенням.

Ніколи не переміщуйте, не видаляйте й не використовуйте повторно тег релізу. Якщо публікація не вдалася після появи версії в npm, збільште версію через новий pull request. За бажанням окремо створіть GitHub Release; публікації npm не потрібні права запису до репозиторію.
