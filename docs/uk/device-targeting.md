# OTA-релізи для вибраних пристроїв {#device-targeted-ota-releases}

Реліз має аудиторію (`all` або `devices`), незалежну від політики доставки та Guard. Аудиторія перевіряється до вибору маніфесту. Середовище виконання, канал і платформа, як і раніше, мають збігатися. Guard примусового оновлення не обходить аудиторію.

## Спочатку smoke-тест, потім реліз {#smoke-test-then-release}

1. Налаштуйте застосунок через `npm run configure-app`. Згенерований `ota-entry.js` запускає клієнт до початкової точки входу Router або власного застосунку; ручне підключення хука чи ID не потрібне. Наявні згенеровані файли можна оновити з `--force` (перевірте локальні зміни).
2. Перезберіть нативний застосунок після додавання `expo-secure-store`; використовуйте нове середовище виконання, щоб старі збірки не завантажували JavaScript, який імпортує відсутній нативний модуль.
3. Відкрийте застосунок. У **Встановлення → Деталі встановлення** скопіюйте ID пристрою або назвіть його **Мій телефон**. Старі клієнти, як і раніше, повідомляють ID встановлення, за яким їх можна вибрати.
4. Опублікуйте через згенеровану команду `npm run ota:publish -- --platform android --message "Smoke"`. Публікація створює чернетку. У її деталях виберіть **Аудиторія оновлення → Лише вибрані пристрої / встановлення**, укажіть телефон і **збережіть до активації**.
5. Активуйте чернетку. Ваш пристрій отримає її; інші сумісні пристрої — попереднє придатне публічне оновлення або відсутність оновлення, якщо такого немає.
6. Після перевірки встановіть аудиторію **Усі сумісні пристрої** та збережіть. Той самий артефакт стає доступним усім; повторна публікація не потрібна.

Зміна активної аудиторії негайно впливає на майбутні перевірки. Вона не видаляє й не відкликає кешовані або завантажені OTA-пакети. Для зміни запущеної версії використовуйте наявний процес відкату. Вибір пристроїв — механізм розповсюдження, а не автентифікація чи конфіденційне сховище: змінений клієнт може передати ID, а URL ресурсів залишаються доступними.

## Два ідентифікатори {#two-identities}

- **ID встановлення (Installation ID)**: випадковий UUID в AsyncStorage. Зберігається під час OTA, змінюється після видалення застосунку або очищення даних. Залишається одиницею підрахунку аналітики встановлень і когорт.
- **ID пристрою (Device ID)**: значення SHA-256 в області ID застосунку та простору імен OTA-сервера. На Android початкове значення — `expo-application.getAndroidId()` (ключ підпису + користувач Android + пристрій). На iOS це випадковий UUID, збережений через `expo-secure-store` з `WHEN_UNLOCKED_THIS_DEVICE_ONLY`, щоб відновлена на іншому телефоні резервна копія навмисно не переносила ідентифікатор. Початкові платформні ID ніколи не надсилаються на сервер.

Перевстановлення Android із тим самим ключем підпису зазвичай зберігає ID пристрою. Скидання до заводських налаштувань, зміна користувача/профілю Android або ключа підпису можуть змінити його. iOS Keychain часто зберігається після перевстановлення з тим самим bundle ID, але це не гарантується. У разі зміни ID пристрою виберіть новий пристрій в аудиторії повторно. Універсального постійного ідентифікатора фізичного пристрою немає. Ім’я в адмінці належить ID пристрою, а не встановлення.

`ota-client/config.json.identityNamespace` зберігається під час повторного налаштування, включно зі зміною URL сервера або тунелю. Зберігайте цей згенерований файл разом із вихідним кодом застосунку. Середовище виконання та канал навмисно не входять до ID пристрою. Окремому застосунку або серверу потрібен власний простір імен.

Офіційні довідники API: [Expo Application](https://docs.expo.dev/versions/v58.0.0/sdk/application/), [Expo SecureStore](https://docs.expo.dev/versions/v58.0.0/sdk/securestore/), [додаткові параметри Expo](https://docs.expo.dev/versions/v58.0.0/sdk/updates/#updatessetextraparamasynckey-value).

## Ініціалізація клієнта {#client-initialization}

Згенерована точка входу автоматично викликає `start()`, зберігає ідентифікатор встановлення й задає `installation_id` / `device_id` через `Updates.setExtraParamAsync`. Сигнал активності додає необов’язковий `deviceId`. Надійна черга та монотонна послідовність для кожного встановлення не змінюються. Недоступний ID пристрою не зупиняє телеметрію встановлень; доставка за пристроями при цьому закрита. Після тимчасового збою Keychain читання ID на iOS повторюється без заміни початкового значення.

Для власного інтерфейсу перевірки й завантаження використовуйте згенеровані `checkForUpdateAsync` і `fetchUpdateAsync`: вони чекають ініціалізації. Прямі виклики `expo-updates` до ініціалізації можуть зробити анонімну перевірку; анонімні клієнти отримують лише публічні оновлення. Конфігурація задає `checkAutomatically: NEVER`, зберігаючи явне керування перевірками. Сам ініціалізатор не завантажує оновлення, не перезапускає застосунок і не змінює навігацію.

Необов’язкові експорти `getInstallationId()` / `getDeviceId()` потрібні для відображення діагностики, а не для реєстрації пристрою. Обидва повертають null, коли оновлення вимкнено (web/dev).

## Міграція та поведінка сервера {#server-migration-and-behavior}

Застосуйте `docs/migrations/2026-10-22-device-targeting.sql` після міграцій аналітики й версій, до розгортання сервера. Нові встановлення використовують `docs/migrations/schema.sql`. Потім застосуйте `docs/migrations/2026-10-22-device-targeting-activation.sql` до розгортання серверних змін за підсумками перехресного рев’ю. Вона атомарно застосовує правила публічної та адресної активації, зберігає деактивацію під час глобальної зупинки й додає дію `ota-force-update` поряд з окремою дією нативного оновлення через магазин. Обидві міграції повторювані й не змінюють аудиторію або активність наявних релізів.

Міграція аудиторії видаляє індекс єдиного активного релізу: адресний реліз має співіснувати з публічним резервним. Наявні релізи мають аудиторію `all`.

Активація, відкат і повернення до останньої версії адресного релізу зберігають інші активні релізи. Звичайна публічна активація, як і раніше, вимикає старі релізи. Розширення вже активного адресного релізу залишає попередній публічний резервний реліз придатним; під час вибору виграє новіший. Вимкнення адресного релізу повертає вибір резервного. Явний відкат пріоритетний, але підпорядковується тим самим перевіркам аудиторії та сумісності. Аварійні закріплені маршрути, як і раніше, закривають видачу, якщо вибраний артефакт відрізняється.

API адмінки:

- `GET/PUT /api/admin/updates/:encodedKey/audience` використовує наявні дозволи читання й запису. PUT замінює режим та обидва списки ID, використовуючи `audience_version` для оптимістичної конкуренції. У режимі `devices` потрібен хоча б один одержувач; максимум 100 ID кожного типу. БД серіалізує зміни аудиторії з аварійним перемикачем розповсюдження.
- `GET /api/admin/device-targets?platform=android|ios` вимагає сесії адмінки й повертає останні 500 встановлень, включно зі старими середовищами виконання. Пошук інтерфейсу показує до 50 збігів; старіші ID можна ввести вручну.
- `PUT /api/admin/device-targets` задає ім’я ID пристрою (лише сесія admin/operator).

Запити маніфесту читають Expo Structured Field Dictionary `Expo-Extra-Params`. Відсутні або некоректні ID ніколи не збігаються із закритою аудиторією. Відповіді використовують `private, no-store`. Придатність перевіряється до запиту резервного останнього активного оновлення, а не після вибору одного нефільтрованого рядка. Прийняті сигнали активності можуть пов’язати нове встановлення з тим самим ID пристрою; повторні та застарілі події не змінюють зв’язок і не об’єднують історію встановлень.

Для ізольованих локальних конфігурацій Docker `configure-app --server-env .env.ota-test` використовує опубліковані порти БД і сховища з цього файла під час створення `.env.ota`.

## Перевірка {#verification}

`npm test`, `npm run lint`, `npx tsc --noEmit` і `npm run installer:check` перевіряють сервер та пакування. Запустіть `OTA_TEST_DATABASE_URL=... node scripts/tests/device-targeting.mjs` на одноразовій тестовій БД із міграціями для реальних перевірок PostgreSQL: придатність, сумісність, CAS, глобальне блокування й перевстановлення. Тестові дані відкочуються. Поведінка перевстановлення та Keychain додатково потребує фізичних пристроїв із нативною збіркою.

Активація та зміна аудиторії серіалізовані в PostgreSQL. Публічна активація вимикає інші активні релізи тієї самої області одним SQL-виразом; невдала активація не може частково вимкнути попередній публічний реліз. Це стосується й наявного редактора `update-meta.json`. Адресна активація зберігає інші аудиторії. Під час глобальної зупинки деактивація може виправити застарілі вказівники на залишений активний резервний реліз; активація, повернення з чинного відкату та зміна аудиторії залишаються заблокованими.

Запустіть `scripts/tests/device-targeting-activation.mjs` на **порожній одноразовій БД** із повною схемою для перевірки паралельних змін аудиторії, атомарності невдалої активації та деактивації під час інциденту. Скрипт відхиляє БД із релізами. Виконавець міграцій аналітики також запускає цей набір для нових встановлень і оновлень.
