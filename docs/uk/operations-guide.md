# Посібник з експлуатації {#operations-guide}

Посібник описує встановлення, повсякденне адміністрування, відновлення після інцидентів, резервне копіювання та оновлення OTA-сервера.

## 1. Потрібна інфраструктура {#_1-required-infrastructure}

- Node.js 24 і npm або Docker із Docker Compose;
- PostgreSQL 15 або новіший;
- S3-сумісне об’єктне сховище, наприклад Cloudflare R2 або MinIO;
- публічний HTTPS URL для production;
- за потреби — CDN перед усім OTA-сервером (він має дотримуватися `Cache-Control: no-store` у відповідях із заблокованими ресурсами).

## 2. Оточення {#_2-environment}

Для ручного встановлення скопіюйте `.env.example` до `.env.local`.

Обов’язкові налаштування PostgreSQL і S3:

```env
DATABASE_PROVIDER=pg
DATABASE_URL=postgresql://user:password@host:5432/database
DATABASE_SSL=true

R2_ENDPOINT=https://storage.example.com
R2_ACCESS_KEY_ID=...
R2_SECRET_ACCESS_KEY=...
R2_BUCKET=expo-updates
R2_REGION=auto

OTA_PUBLIC_BASE_URL=https://updates.example.com
```

Для MinIO також задайте:

```env
S3_FORCE_PATH_STYLE=true
```

Ніколи не додавайте до Git `.env.local`, паролі БД, ключі сховища, токени доступу або приватні ключі підпису коду.

## 3. Встановлення бази даних {#_3-database-installation}

Для PostgreSQL або Supabase застосуйте єдину канонічну схему:

```bash
psql "$DATABASE_URL" -f docs/migrations/schema.sql
```

Встановлення через Supabase SQL Editor описане в [`supabase-setup.md`](supabase-setup.md).

Схема ідемпотентно створює об’єкти й може додати відсутні до наявного встановлення. Перед застосуванням створіть резервну копію БД.

## 4. Перший адміністратор {#_4-first-administrator}

Інтерактивно створіть користувача або скиньте його дані:

```bash
npm run create-admin
```

Ролі:

| Роль | Дозволи |
|---|---|
| `admin` | Повний доступ і керування токенами доступу |
| `operator` | Керування оновленнями та аварійними маршрутами |
| `viewer` | Лише читання |

Паролі мають містити щонайменше 12 символів. Зберігаються лише bcrypt-хеші.

## 5. Ручний запуск {#_5-manual-startup}

До запуску створіть [пару ключів підпису](./expo-app-setup.md#_2-create-the-code-signing-certificate) і задайте в `CODE_SIGNING_PRIVATE_KEY_PATH` абсолютний шлях до приватного ключа. Процес сервера має мати право читання; публічний сертифікат збережіть для застосунку. Ендпоїнт стану нижче перевіряє БД, а не готовність підпису або сховища.

```bash
npm ci
npm run build
npm run start
```

Готовність:

```bash
curl -fsS http://localhost:3000/api/health
```

Очікувана відповідь:

```json
{
  "status": "ok",
  "checks": {
    "database": "ok"
  }
}
```

## 6. Швидкий запуск Docker Compose {#_6-docker-compose-quick-start}

```bash
cp .env.docker.example .env
```

Замініть обидва паролі в `.env`. До запуску створіть або скопіюйте приватний ключ підпису:

```bash
mkdir -p secrets
cp /secure/path/code-signing-private-key.pem \
  secrets/code-signing-private-key.pem
chmod 600 secrets/code-signing-private-key.pem
```

Потім запустіть стек:

```bash
docker compose up -d --build
docker compose ps
```

Якщо порт `3000` зайнятий, оновіть обидва значення в `.env`:

```env
OTA_HTTP_PORT=3100
OTA_PUBLIC_BASE_URL=http://localhost:3100
```

Сервіси:

- адмінка та OTA-сервер: `http://localhost:3000`;
- консоль MinIO: `http://localhost:9001`;
- PostgreSQL і MinIO API доступні лише всередині мережі Compose.

Приватний ключ монтується лише для читання в `/run/secrets/ota/code-signing-private-key.pem`. Публічний сертифікат має бути в кожному застосунку Expo, а не в контейнері сервера.

На новому томі PostgreSQL автоматично застосовується `docs/migrations/schema.sql`. Створіть першого адміністратора всередині контейнера застосунку:

```bash
docker compose exec app npm run create-admin
```

Зупинка без видалення даних:

```bash
docker compose down
```

Видаляйте локальну БД та об’єктне сховище лише за навмисного повного скидання:

```bash
docker compose down --volumes
```

Зміна `POSTGRES_PASSWORD` у `.env` не змінює пароль ролі в наявному томі PostgreSQL. Синхронізуйте його без видалення даних:

```bash
npm run docker:sync-db-password
docker compose restart app
```

## 7. Токени доступу {#_7-access-tokens}

Токени доступу призначені для CI, скриптів і майбутнього CLI публікації. Мобільні пристрої їх не надсилають.

Створюйте їх через `POST /api/admin/access-tokens` з авторизацією `admin`. Одразу збережіть повернений початковий токен: він показується лише один раз.

Приклад:

```bash
curl \
  -H "Authorization: Bearer $OTA_ACCESS_TOKEN" \
  https://updates.example.com/api/admin/updates
```

Доступні дозволи:

- `updates:read`;
- `updates:write`;
- `redirects:read`;
- `redirects:write`.

Негайно відкликайте невикористовувані або розкриті токени.

## 8. Оновлення та відкат {#_8-updates-and-rollback}

Список оновлень розташований у `/updates`.

- **Деактивувати** припиняє видачу оновлення.
- **Відкат** закріплює канал за старішим активним оновленням.
- **Повернути останнє** завершує режим відкату й відновлює видачу останнього оновлення.
- Під час звичайної роботи не редагуйте вказівники каналів безпосередньо в PostgreSQL.

Після відкату перевірте обидві платформи й точну область runtime/каналу.

## 9. Аварійні маршрути {#_9-emergency-redirects}

Правила керуються в `/updates/emergency-redirects`.

Спочатку використовуйте `pinned`:

1. Укажіть точні ID вбудованого оновлення, runtime, платформу й початковий канал.
2. Задайте правильний цільовий канал.
3. Закріпіть ID перевіреного оновлення для відновлення.
4. Переконайтеся, що проблемна збірка отримує й запускає OTA відновлення.
5. Перемкніться в `follow`, щоб стара збірка отримувала майбутні оновлення цільового каналу.

Під час переходу зі старої JSON-конфігурації:

```bash
npm run emergency:import
```

Після міграції обробник маніфестів читає лише `ota_emergency_redirects`.

## 9.1 Глобальний аварійний перемикач OTA {#_9-1-global-ota-emergency-switch}

Основний елемент керування на `/updates` — перемикач інциденту з найвищим пріоритетом. У стані **BLOCKED**:

- кожен запит маніфесту отримує підписану директиву Expo `noUpdateAvailable`;
- кожен запит `/api/assets` закриває видачу з `503` і `Cache-Control: no-store`;
- активація, відкат, повернення до останнього та зміни розповсюдження `channel-latest.json` / `update-meta.json` повертають `409`;
- активація оновлень і зміни розповсюдження каналів також відхиляються PostgreSQL із SQLSTATE `P0OTA` та повідомленням `OTA_DISTRIBUTION_BLOCKED`, включно зі звичайними прямими SQL-записами;
- деактивація, додавання неактивних чернеток, безпечне редагування метаданих та очищення вказівників каналів, яке не залишає виданого оновлення, доступні. Видалення оновлення доступне лише тоді, коли очищення вказівників зовнішніх ключів не просуне й не перенаправить інше оновлення.

Увімкнення вимагає причини й підтвердження. Вимкнення теж вимагає підтвердження. Спостерігачі бачать стан, але не можуть його змінювати. Зміни використовують оптимістичну версію й записуються з виконавцем і часом. RPC перемикача та тригери розповсюдження поділяють транзакційне блокування БД: паралельна зміна або завершується до BLOCKED, або чекає й відхиляється; вікна між перевіркою та зміною немає. Не вимикайте ці тригери під час інциденту.

Порядок дій під час інциденту:

1. Відкрийте `/updates`, укажіть інцидент/завдання та вплив у причині, потім виберіть **Зупинити всі OTA**.
2. Підтвердьте результат перевірки маніфесту (`noUpdateAvailable`) і раніше виданого URL `/api/assets` (`503`, no-store).
3. Досліджуйте або деактивуйте проблемні оновлення за заблокованого розповсюдження.
4. Перед відновленням перевірте вказівники каналів та обидві платформи.
5. Виберіть **Відновити OTA**, підтвердьте та повторіть перевірки маніфестів.

Перемикач вимагає міграції `docs/migrations/2026-09-02-ota-distribution-control.sql`. Відсутня таблиця або помилка читання БД навмисно не трактуються як ACTIVE: видача маніфестів і ресурсів закривається.

`OTA_CDN_BASE_URL` збережено лише як застаріле налаштування. Нові маніфести завжди використовують перевірювані URL `/api/assets` сервера. Зовнішній CDN розміщуйте перед OTA-сервером, а не відкривайте URL бакета, і переконайтеся, що CDN дотримується відповіді `private, no-store`. Перемикач не відкликає незмінні старі URL сховища/CDN, уже видані попередньою версією сервера; очистіть або вимкніть старий CDN, перш ніж покладатися на перемикач для цих маніфестів.

## 10. Резервні копії {#_10-backups}

PostgreSQL:

```bash
pg_dump --format=custom "$DATABASE_URL" > ota-database.dump
```

Відновлення в порожню БД:

```bash
pg_restore --clean --if-exists --dbname="$DATABASE_URL" ota-database.dump
```

Об’єктне сховище потрібно копіювати окремо засобами реплікації, версіонування або S3-синхронізації провайдера. Резервної копії БД без ресурсів недостатньо для відновлення доставки OTA.

Для томів Docker:

```bash
docker compose exec -T postgres \
  pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=custom \
  > ota-database.dump
```

## 11. Безпечний порядок оновлення {#_11-safe-upgrade-order}

1. Створіть резервні копії PostgreSQL та об’єктного сховища.
2. Прочитайте нові файли міграцій.
3. Застосуйте зворотно сумісні міграції.
4. Виконайте тести й зберіть новий образ.
5. Розгорніть застосунок.
6. Перевірте `/api/health`.
7. Перевірте запити маніфестів production-областей iOS і Android.
8. Збережіть попередній образ для відкату застосунку.

Не розгортайте код, який читає нову таблицю, до її створення.

### Міграція ідентифікаторів маніфестів (2026-10-16) {#manifest-identity-migration-2026-10-16}

Застосуйте `docs/migrations/2026-10-16-manifest-identity.sql` до розгортання відповідного серверного коду. Нові встановлення отримують зміни зі `schema.sql`. На наявних уже має бути міграція керування розповсюдженням, описана вище.

Для цього оновлення зупиніть розповсюдження OTA, застосуйте міграцію, замініть усі екземпляри сервера й потім відновіть розповсюдження. Не обслуговуйте трафік сумішшю старих і нових екземплярів: старий код може повернути маніфест навіть за помилки асинхронного запису зіставлення. Відкат до нього повертає помилку ідентифікації; самих нових SQL-тригерів недостатньо.

Кожен UUID маніфесту тепер обчислюється з епохи публікації каналу та UUID реально вибраного оновлення. Тому неактивне завантаження може використовувати стабільне резервне оновлення, не поділяючи його ID маніфесту з майбутнім активованим оновленням. Активація просуває епоху каналу, навіть якщо вказівник latest не змінився. Зміни вказівників і повторні відкати просувають годинник епохи щонайменше на мілісекунду, зберігаючи порядок публікацій для Expo.

Сервер записує зіставлення маніфесту з оновленням до повернення маніфесту. Відсутні таблиці зіставлення, помилки пошуку або запису тепер завершують запит помилкою замість непомітної зміни ID або втрати історії. Повтор однакового зіставлення допустимий; призначення наявного ID маніфесту іншому оновленню або області відхиляється PostgreSQL. Відповідям без оновлення нове зіставлення не потрібне.

Наявні записи зберігаються й читаються новим сервером. Раніше перезаписані історичні зіставлення автоматично не відновлюються. Зміна захищає зв’язок ID та оновлення; вона не заморожує всі опубліковані JSON/ресурси й не змінює політику видалення або зберігання. Поточні ID каналів в адмінці позначають епохи публікації, а не похідні UUID, що повертаються пристроям.

SQL-скрипт регресії можна запустити на **одноразовій** БД після застосування схеми та міграції:

```bash
psql "$OTA_TEST_DATABASE_URL" -v ON_ERROR_STOP=1 \
  -f scripts/tests/manifest-identity.sql
```

Він перевіряє активацію чернеток, повторні активації/відкати, монотонність годинника, глобальний захист розповсюдження та незмінні upsert-зіставлення. Він тимчасово змінює глобальний перемикач і відкочує тестові дані; не запускайте його на робочій БД OTA.

## 12. Підключення застосунку Expo {#_12-expo-application-integration}

Конфігурація клієнта, сертифікати підпису, реєстрація вбудованих оновлень, ручні перевірки та поточна публікація описані в [`expo-app-setup.md`](expo-app-setup.md).

## Телеметрія встановлень {#installation-telemetry}

Після міграцій ідентифікаторів маніфестів і керування розповсюдженням вище застосуйте файли по черзі до розгортання оновленого сервера:

```sh
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 \
  -f docs/migrations/2026-10-19-device-heartbeat.sql \
  -f docs/migrations/2026-10-22-device-analytics.sql \
  -f docs/migrations/2026-10-22-device-version-metadata.sql \
  -f docs/migrations/2026-10-22-device-targeting.sql \
  -f docs/migrations/2026-10-22-device-targeting-activation.sql
```

Нові встановлення використовують лише `schema.sql`, який уже містить зміни. Повторне застосування зберігає початок збору, записи встановлень та аудиторії релізів. Остання міграція переносить публічну й адресну активацію до атомарної операції БД, допускає очищення під час деактивації за глобальної зупинки та додає окрему дію `ota-force-update`. Застосуйте її до відповідного сервера.

Повторно запустіть стандартний конфігуратор застосунку для встановлення клієнта ідентифікації/телеметрії та кореневого підключення `useOtaUpdates`/`OtaUpdateGate`. Додавання SecureStore або інших нативних залежностей клієнта потребує нативної перезбірки із сумісним runtime; не публікуйте JavaScript з імпортом недоступних нативних модулів для старого runtime. Клієнти, які вже надсилають сигнали активності, можуть заповнювати аналітику без перезбірки, але нові ID пристрою та життєвий цикл хука потребують оновленого клієнта. Див. [життєвий цикл клієнта](./ota-client-lifecycle.md) та [вибір пристроїв](./device-targeting.md).

Сторінка **Встановлення** (`/updates/devices`) показує поточні запуски за версіями, денну активність і когорти. Денна історія починається з міграції; історія до оновлення недоступна. Утримання використовує незалежне вікно 90 днів і повністю спостережувані наступні дні. Наявні встановлення залишаються видимими в когортах поточного складу. Точні правила фільтрів і вікон, перевірки міграцій, контракт подій, поведінку точки входу, доступ та обмеження див. у [телеметрії встановлень](./installation-telemetry.md).
