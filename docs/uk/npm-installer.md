# Створення сервера через NPX {#create-a-server-with-npx}

npm-ініціалізатор — найшвидший спосіб створити самостійну копію Expo Updates Server. Потрібен Node.js 20.9 або новіший.

```bash
npx create-expo-updates-server@latest my-server
cd my-server
```

Також можна ініціалізувати порожній поточний каталог:

```bash
mkdir my-server
cd my-server
npx create-expo-updates-server@latest .
```

`npx` завантажує опублікований пакет ініціалізатора з npm. Після запуску сам ініціалізатор не робить мережевих запитів: шаблон сервера та його маніфест SHA-256 включені до пакета.

Для іменованого каталогу успішний текстовий вивід має такий вигляд (інтерактивні термінали додають колір):

```text
✓ Expo Updates Server project files created
Project: /path/to/my-server

Next steps (Docker):
  1. cd -- 'my-server'
  2. npm ci
  3. Follow docs/getting-started.md: prepare settings and signing keys before starting Docker.

Next steps (npm):
  1. cd -- 'my-server'
  2. npm ci
  3. Follow docs/operations-guide.md: configure database, storage and signing keys before startup.
```

За використання `.` зайвий крок `cd` пропускається. Колір вимкнено, якщо вивід не є TTY або задано змінну оточення `NO_COLOR`.

## Безпека встановлення {#safety-behavior}

Ініціалізатор:

- приймає рівно один каталог призначення;
- вимагає, щоб іменований шлях призначення не існував, і відхиляє наявні порожні й непорожні каталоги, файли та символічні посилання;
- приймає наявний каталог лише тоді, коли це саме поточний каталог без видимих або прихованих елементів;
- створює унікальний сусідній тимчасовий каталог із правами `0700`;
- збирає весь проєкт у тимчасовому каталозі та перевіряє повний набір шляхів, типи файлів, розміри й хеші SHA-256 до встановлення;
- встановлює відсутній іменований каталог перейменуванням тимчасового каталогу;
- безпосередньо перед встановленням у `.` повторно перевіряє пристрій, inode і порожність поточного каталогу, створює каталоги виключно, копіює файли без перезапису й перевіряє підсумковий набір шляхів, розміри та хеші SHA-256;
- ніколи не перезаписує елементи, виявлені під час встановлення в `.`, і ніколи не видаляє поточний каталог рекурсивно;
- після початку підготовки залишає унікальний тимчасовий каталог у разі помилки та повідомляє його точний шлях для ручної перевірки або видалення; якщо в `.` залишився частковий результат встановлення, про нього також повідомляється.

Іменований каталог призначення має бути відсутнім протягом усієї команди. Якщо інший процес створить файл, символічне посилання або непорожній каталог до остаточного перейменування, ініціалізатор завершиться з помилкою та залишить його без змін. Переносні файлові API не надають кросплатформного атомарного перейменування каталогу без перезапису. У вузькому вікні гонки, коли інший процес створює порожній каталог призначення після останньої перевірки відсутності, перейменування може замінити цей порожній каталог.

Встановлення в `.` переносить елементи, а не замінює сам поточний каталог. Виключні операції запобігають перезапису елемента, який з’явився за шляхом призначення під час звичайної паралельної роботи. Якщо встановлення завершиться помилкою після створення частини елементів, їх навмисно не видаляють: їх уже не можна безпечно відрізнити від змін користувача. Вручну перевірте вказаний поточний каталог і тимчасовий знімок. Ці перевірки захищають від звичайних гонок файлової системи, а не від іншого процесу того самого користувача.

Тимчасовий каталог містить лише публічні файли шаблону. У разі успіху він стає іменованим каталогом призначення або видаляється після перевіреного перенесення в `.`, тому тимчасових каталогів не залишається.

Ініціалізатор навмисно не встановлює залежності, не створює Git-репозиторій, не записує `.env` і не генерує ключі підпису або інші секрети. Параметра `--force` немає.

## Запуск створеного проєкту {#start-the-generated-project}

Послідовно виконайте вбудований посібник [«Швидкий старт»](./getting-started.md): оточення, ключі підпису, запуск Docker, адміністратор, URL для телефона, налаштування застосунку, нативна збірка та перше OTA. Для `configure-app` на хості потрібні Node/npm і `npm ci`, навіть якщо сервер працює в Docker.

Для розміщеної інфраструктури скористайтеся [налаштуванням Supabase](./supabase-setup.md) і [посібником з експлуатації](./operations-guide.md). Налаштуйте БД, сховище та ключ підпису до запуску сервера через npm.

Пакет містить шаблон із зафіксованого коміту вихідного коду. Неопублікована функція в робочій копії недоступна через `npx ...@latest`; супроводжувачам слід дотримуватися [процесу релізу](./publishing-npm-installer.md).

## Відтворюваність і вихідний код {#reproducibility-and-source}

Кожен опублікований пакет містить відфільтрований знімок, байти якого читаються безпосередньо з об’єктів Git зафіксованого коміту в [tonichiga/expo-updates-server](https://github.com/tonichiga/expo-updates-server). Змінені або невідстежувані файли робочої копії не впливають на цей знімок. Пакет записує точний коміт, розмір і SHA-256 кожного створюваного файла. Результати збірки, облікові дані, заповнені секретні значення, реальні файли оточення, внутрішні плани та сам ініціалізатор виключені.
