# Клієнтський контракт політики OTA-оновлень {#ota-update-policy-client-contract}

Кожен виданий маніфест оновлення містить `extra.updatePolicy`:

```json
{
  "schemaVersion": 1,
  "policyVersion": 2,
  "delivery": "background",
  "guard": {
    "action": "require-confirmation",
    "payload": { "message": "Restart when ready" }
  }
}
```

Властивість `guard` відсутня, якщо Guard не налаштовано. Налаштований Guard безумовний: він включається для кожного клієнта, якому наявна логіка вибору за середовищем виконання, каналом, платформою, аудиторією та оновленням видає це OTA. Примусовий Guard ніколи не обходить аудиторію пристроїв. Наявність дії в каталозі рекомендаційна й не потрібна для її збереження або видачі.

- `Updates.checkForUpdateAsync()` повертає політику в маніфесті **кандидата** в результаті перевірки.
- `Updates.manifest` містить політику оновлення, **запущеного зараз**. Не використовуйте її як політику кандидата до завантаження.
- `manual` використовується за замовчуванням і залишає завантаження та перезапуск застосунку.
- `background` означає непомітне завантаження кандидата без негайного перезапуску та застосування під час наступного холодного старту.
- Старі клієнти безпечно ігнорують додаткове значення `extra`.

Неактивне завантаження є чернеткою, навіть якщо його початковий `disabled_at` дорівнює `created_at`. Режим доставки та простий Guard можна редагувати до активації. Сам по собі `disabled_at` не доводить, що оновлення публікувалося.

`ota_update_channels.latest_update_id` позначає найновіше завантаження й тому може вказувати на неактивну чернетку. Цей вказівник не доводить публікацію; під час вибору маніфесту використовується останнє активне оновлення. Вказівник відкату `active_update_id` або запис у `ota_served_manifest_log` підтверджують публікацію.

Активація є подією публікації. Після активації, повернення до останньої версії, використання як цілі відкату або підтвердженої видачі політика залишається незмінною, навіть якщо потім оновлення вимкнули. Щоб змінити політику, опублікуйте новий ID оновлення.

## Порядок оновлення production {#production-upgrade-order}

Створіть резервну копію БД. Для наявних встановлень застосуйте ці ідемпотентні міграції по черзі:

```bash
psql "$DATABASE_URL" -f docs/migrations/2026-09-01-p1-guard-actions.sql
psql "$DATABASE_URL" -f docs/migrations/2026-09-01-p2-simplify-ota-guard-policy.sql
psql "$DATABASE_URL" -f docs/migrations/2026-09-01-policy-publication-correction.sql
```

Міграція спрощення навмисно видаляє `guard_rules` без перетворення старих правил. Вона додає стовпці `guard_action` і `guard_payload`, що допускають null, та перестворює тригер незмінності політики для простої моделі. Остання коригувальна міграція очищає лише помилково визначені маркери публікації для консервативно вибраних неактивних стандартних політик, які ніколи не видавалися. Вона не розблоковує активні оновлення, цілі відкату або вже видані оновлення.

Оточення, де вже успішно виконано `2026-09-01-policy-publication-correction.sql` і підтверджено відсутність чернеток, помилково позначених опублікованими, можуть пропустити третій крок. Інакше корекція має йти третьою, оскільки звертається до стовпців `guard_action` і `guard_payload`, створених міграцією спрощення.

Користувачі Supabase можуть виконати ті самі файли в SQL Editor у вказаному порядку. Для нових встановлень застосовуйте лише канонічний `docs/migrations/schema.sql`, який уже містить просту модель.

## Каталог дій Guard {#guard-action-catalog}

Редактор політики завантажує назви дій для повторного використання з `ota_guard_actions`. Нові встановлення отримують окремі дії `ota-force-update` та `ota-force-store-update`. Оператори можуть створити дію, ввівши її в поле вибору, або через окрему форму каталогу. Ця форма доступна й під час перегляду незмінної політики та ніколи її не змінює.

Збережені записи каталогу можна видалити кнопкою кошика. Видалення з каталогу не змінює наявну політику. Її дія залишається видимою як тимчасовий варіант до явної зміни; такі варіанти не мають кнопки видалення.

Під час створення ключі дій обрізаються по краях, мають містити 1–100 символів і не можуть містити керувальних символів. Спостерігачі можуть переглядати каталог, але не створювати й не видаляти записи.

## Згенерований клієнтський хук {#generated-client-hook}

Конфігуратор встановлює `useOtaUpdates(options)` і автоматично підключає його в кореневому layout/App з `OtaUpdateGate` навколо вмісту застосунку. Налаштування та методи описані в [посібнику з життєвого циклу клієнта](./ota-client-lifecycle.md). Хук оцінює політику кандидата з `check()`, потім повторно перевіряє завантажений маніфест: вибраний реліз може змінитися між перевіркою та завантаженням.

- `ota-force-update` вимагає сумісне **OTA**: блокувальний екран забороняє взаємодію, хук завантажує оновлення й показує дію перезапуску після готовності.
- `ota-force-store-update` вимагає **нову нативну збірку**: екран відкриває URL магазину для платформи й не завантажує цього OTA-кандидата. OTA не може змінити середовище виконання або додати нативні модулі. Додаткові дані підтримують `androidUrl`, `iosUrl` або спільний резервний `url`.
- Невідомі та власні дії залишаються заблокованими, доки явний `guardHandlers[action]` не поверне `allow`. Сам запис у каталозі не реалізує поведінку Guard.
- `delivery: background` завантажує непомітно й чекає холодного запуску або ручного перезапуску. Увімкнений `autoReload` не спричиняє негайного перезапуску.
- Кандидат із ручною доставкою показується для явного завантаження й перезапуску, якщо кореневі налаштування не вмикають `autoUpdate`/`autoReload`. Згенерований корінь вмикає лише автоматичні перевірки.

Блокувальний екран потрібен для блокування інтерфейсу застосунку; один хук лише надає стан. Поки обов’язкового кандидата не виявлено, помилка перевірки без мережі залишає запущений застосунок доступним. Expo може застосувати раніше завантажений пакет під час нативного запуску; JavaScript не може відкликати цей нативний кеш. Це політики доставки, а не автентифікація клієнта. Старі клієнти можуть ігнорувати поля політики, тому спочатку поширте налаштований нативний клієнт і лише потім покладайтеся на Guard.

Наявні встановлення отримують нову дію OTA Guard через `2026-10-22-device-targeting-activation.sql`, після міграцій аудиторії з [посібника з експлуатації](./operations-guide.md#installation-telemetry). Міграція ідемпотентна й не переписує опубліковані політики.
