# Публикация `create-expo-updates-server` {#publishing-create-expo-updates-server}

Корневой пакет Next.js остаётся закрытым. Публикуется только рабочий пакет `packages/create-expo-updates-server`.

## Однократная настройка npm {#one-time-npm-configuration}

До любой публикации защитите окружение GitHub `npm-publish`, назначив обязательных проверяющих релиза. Обычные релизы используют npm Trusted Publishing и workflow `.github/workflows/publish-create-expo-updates-server.yml` только с OIDC; npm-токен не используется.

### Первая публикация {#first-publication}

Сначала попробуйте настроить npm **Trusted Publisher** для `tonichiga/expo-updates-server`, workflow `.github/workflows/publish-create-expo-updates-server.yml` и окружения `npm-publish`.

Если npm требует существования пакета для такой настройки, уполномоченный сопровождающий может выполнить ровно одну ручную публикацию:

1. Выполните проверки релиза ниже, затем соберите один архив командой `npm pack --workspace create-expo-updates-server`. Проверьте `.tgz` и сохраните проверенный файл без повторной сборки.
2. На доверенном компьютере сопровождающего войдите в npm с одноразовым кодом OTP и выполните `npm publish <reviewed-tarball> --access public`. Не добавляйте `--provenance`: у первой ручной публикации не будет подтверждения происхождения от GitHub.
3. Сразу настройте Trusted Publisher, описанный выше.

Никогда не сохраняйте токен публикации npm в GitHub, репозитории, workflow или файле сопровождающего. Начального workflow с токеном нет. Все последующие публикации должны использовать Trusted Publishing по тегу.

## Процедура релиза {#release-procedure}

1. Создайте ветку от актуального `main`.
2. Увеличьте `version` в `packages/create-expo-updates-server/package.json` и выполните `npm install`, чтобы корневой lock-файл зафиксировал точно такую же версию рабочего пакета.
3. Выполните:

   ```bash
   npm ci
   npm run installer:check
   npm run installer:pack-smoke -- --docker
   npm run docs:build
   ```

   Нужны работающие Docker Engine и Compose 2.24.4+. Smoke-тест с `--docker` запускает проект, созданный из упакованного npm-артефакта, с новыми томами, временными учётными данными и ключами, а также случайными loopback-портами. Он проверяет состояние БД, доступ к ключу подписи, загрузку и скачивание ресурсов, повторяемую инициализацию бакета, затем удаляет только собственные контейнеры и тома. Первая сборка MinIO из исходников занимает несколько минут. Без `--docker` проверяются только создание проекта и установка зависимостей.

4. Откройте pull request и объедините его только после успешных CI и ревью.
5. На объединённом коммите создайте и отправьте тег строго такого вида:

   ```text
   create-expo-updates-server-v<version>
   ```

   Например, для версии пакета `0.2.0` нужен тег `create-expo-updates-server-v0.2.0`.

Workflow, запускаемый только по тегу, сверяет тег с версией пакета, повторно собирает и тестирует детерминированный шаблон и проверяет, что отмеченный коммит является предком `origin/main`. Проверка выполняется до входа в защищённое окружение `npm-publish`. Создаётся один архив релиза; именно этот артефакт передаётся заданию публикации с защитой окружением и публикуется с публичным доступом и npm provenance через OIDC. Несовпадение тега, не включённый в main коммит или несовпадение SHA рабочей копии и события блокируют публикацию.

У задания публикации есть только `contents: read` и `id-token: write`; доступ к npm обеспечивает Trusted Publishing. Не расширяйте разрешения и не переносите шаги сборки в задание с защищённым окружением.

Никогда не перемещайте, не удаляйте и не используйте повторно тег релиза. Если публикация не удалась после появления версии в npm, увеличьте версию через новый pull request. При желании отдельно создайте GitHub Release; публикации npm не нужны права записи в репозиторий.
