# Диагностика настройки с doctor {#diagnose-setup-with-doctor}

Запускайте `doctor` из **каталога сервера**. Он проверяет сервер и, при необходимости, приложение Expo, не меняя файлы, не запуская контейнеры, не применяя миграции, не загружая ресурсы и не активируя обновления. Рекомендуется Node.js 24; парсер env требует Node.js 20.12+. Для проверки назначения сертификата также нужен исполняемый файл OpenSSL.

```bash
npm ci
npm run doctor -- --app ../my-expo-app
```

По умолчанию используется **режим Docker** с `.env` и `docker-compose.yml`. Сервис `app` должен работать. Проверки БД, бакета и ключа подписи выполняются внутри контейнера от его обычного пользователя, поэтому проверяют реальный доступ контейнера, а не права хоста на чтение подключённого ключа.

Чтобы до запуска проверить только файлы сервера:

```bash
npm run doctor -- --offline --certificate ./local-certificates/code-signing-certificate.pem
```

Автономные проверки Docker используют сопоставление env стандартного шаблона и путь ключа на хосте `secrets/code-signing-private-key.pem`. Они не вычисляют пользовательские переопределения Compose и не доказывают, что контейнер может прочитать ключ.

## Удалённое развёртывание или запуск через npm {#remote-or-npm-deployment}

Выберите удалённый режим явно. Он читает **только** выбранный env-файл, не подмешивая учётные данные оболочки и не загружая неявно другой `.env.local`:

```bash
npm run doctor -- \
  --mode remote \
  --server-env ./server.env \
  --app ../my-expo-app
```

Режим поддерживает конфигурации PostgreSQL/S3 и Supabase. Запускайте его там, где доступны env-файл, закрытый ключ, БД и хранилище. Относительные пути к закрытому ключу отсчитываются от каталога сервера. Имя хоста не подразумевает SSH-подключение или доступ к удалённой файловой системе. Подстановка переменных env в удалённом режиме не выполняется; используйте явные значения. URL PostgreSQL должен содержать пользователя, пароль и БД; из параметров URL поддерживается только `sslmode`. Порт по умолчанию явно равен 5432, поэтому внешние переменные `PG*` не могут незаметно выбрать другое подключение.

## Собственный проект Docker {#custom-docker-project}

Передайте те же проект и файлы Compose, которые использовались при запуске, в том же порядке:

```bash
npm run doctor -- \
  --server-env .env.ota-test \
  --project ota-test \
  --compose-file docker-compose.yml \
  --compose-file docker-compose.ota-test.yml \
  --app ../rn-app-ota-test
```

`--compose-file` можно повторять. Эти тестовые файлы относятся к локальному стенду; для созданного проекта используйте свои. Настройки подключения и контекста Docker передаются, а произвольные env-переопределения приложения из оболочки — нет. Сетевая проверка читает окружение работающего приложения и сообщает о несовпадении публичного URL с выбранным env-файлом.

## Что проверяется {#what-is-checked}

| Область | Проверки |
| --- | --- |
| Среда выполнения | Парсер env Node и зависимости сервера |
| Окружение | Явный env-файл, значения-заглушки, особенности экранирования Docker |
| Подпись | Читаемый RSA-ключ не короче 2048 бит, действующий публичный сертификат не-CA, назначения Digital Signature / Code Signing, совпадение публичных ключей |
| URL сервера | Корректный публичный URL, доступ хоста к `/api/health`, оговорки о loopback и HTTP |
| PostgreSQL | Подключение, чтение основных столбцов OTA/телеметрии/аудитории, необходимые сигнатуры таблиц и функций, включённый триггер активации аудитории |
| Supabase | Чтение основных REST-таблиц, столбцов и бакета; тела SQL-функций не проверяются |
| Хранилище | Наличие и доступность бакета через S3 HEAD или Supabase bucket GET; без записи |
| Приложение Expo | Статическая конфигурация, установленные клиентские зависимости, файлы реализации, URL/канал/runtime, нативный режим проверки, пространство идентификаторов и URL телеметрии |
| Корень приложения | Распознанное подключение хука и блокирующего экрана, сгенерированные метаданные начальной загрузки; пользовательские корни требуют ручной проверки |
| Публикатор/регистратор | Наличие и базовая структура учётных данных `.env.ota`, команда публикации, согласованность канала и URL регистрации |

Без `--app` проверки приложения пропускаются. Без сертификата приложения или явного `--certificate` сравнение пары ключей пропускается. Явный сертификат имеет приоритет над сертификатом приложения; если это другой файл, выводится предупреждение. Doctor никогда не выполняет `app.config.*`; для таких проектов сообщает об ограничении статической конфигурацией.

Каждая проверка возвращает `pass`, `fail`, `warn` или `skip`, а при необходимости — конкретный способ исправления. Необработанные исключения, учётные данные, закрытые ключи и строки подключения в вывод не включаются.

## CI и тайм-ауты {#ci-and-timeouts}

```bash
npm run --silent doctor -- --mode remote --server-env ./server.env --json
```

Используйте `--silent`, чтобы npm не добавлял заголовок команды перед JSON. Вывод имеет версионируемую структуру:

```json
{
  "version": 1,
  "mode": "remote",
  "offline": false,
  "status": "fail",
  "checks": [
    {
      "id": "signing.key",
      "status": "fail",
      "message": "Signing key is missing, unreadable or invalid.",
      "remedy": "Check the signing key configuration and read permissions."
    }
  ]
}
```

Коды завершения: `0` — блокирующих проблем не обнаружено (могут остаться предупреждения и пропуски), `1` — проверки не пройдены, `2` — неверные аргументы или неожиданная ошибка диагностики. `--timeout 10000` разрешает 10 секунд на сетевую операцию; поддерживается 500–30000 мс. Некоторые проверки последовательны, поэтому суммарное время может превышать один тайм-аут. Выполнение Docker также ограничено общим временем.

## Чего успешная проверка не доказывает {#what-a-pass-does-not-prove}

Doctor не проверяет нативные SDK и инструменты, не выполняет сборки, не сравнивает все определения миграций и не проверяет права записи. Наличие токена не доказывает его разрешения. Учётные данные приложения могут отличаться от серверных; авторизацию публикатора и регистратора нужно проверить реальной сборкой и публикацией. Настройки контейнера, кроме публичного URL, проверяются в работающем состоянии, а не исчерпывающе сравниваются с ожидающими изменениями Compose.

Доступность URL с хоста не доказывает доступность с телефона. Конфигурация исходников также не доказывает, какие URL/runtime/сертификат установлены в нативной сборке. После исправления выполните [быстрый старт](./getting-started.md) или [проверку на новом приложении](./expo-app-setup.md#verify-generation-in-a-fresh-application): сборка → установка → публикация → активация → скачивание → перезапуск.
