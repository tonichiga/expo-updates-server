# Руководство по эксплуатации {#operations-guide}

Руководство описывает установку, повседневное администрирование, восстановление после инцидентов, резервное копирование и обновление OTA-сервера.

## 1. Необходимая инфраструктура {#_1-required-infrastructure}

- Node.js 24 и npm либо Docker с Docker Compose;
- PostgreSQL 15 или новее;
- S3-совместимое объектное хранилище, например Cloudflare R2 или MinIO;
- публичный HTTPS URL для production;
- при необходимости — CDN перед всем OTA-сервером (он должен соблюдать `Cache-Control: no-store` в ответах с заблокированными ресурсами).

## 2. Окружение {#_2-environment}

Для ручной установки скопируйте `.env.example` в `.env.local`.

Обязательные настройки PostgreSQL и S3:

```env
DATABASE_PROVIDER=pg
DATABASE_URL=postgresql://user:password@host:5432/database
DATABASE_SSL=true

R2_ENDPOINT=https://storage.example.com
R2_ACCESS_KEY_ID=...
R2_SECRET_ACCESS_KEY=...
R2_BUCKET=expo-updates
R2_REGION=auto

OTA_PUBLIC_BASE_URL=https://updates.example.com
```

Для MinIO также задайте:

```env
S3_FORCE_PATH_STYLE=true
```

Никогда не добавляйте в Git `.env.local`, пароли БД, ключи хранилища, токены доступа или закрытые ключи подписи кода.

## 3. Установка базы данных {#_3-database-installation}

Для PostgreSQL или Supabase примените единую каноническую схему:

```bash
psql "$DATABASE_URL" -f docs/migrations/schema.sql
```

Установка через Supabase SQL Editor описана в [`supabase-setup.md`](supabase-setup.md).

Схема идемпотентно создаёт объекты и может добавить недостающие в существующей установке. Перед применением создайте резервную копию БД.

## 4. Первый администратор {#_4-first-administrator}

Интерактивно создайте пользователя или сбросьте его данные:

```bash
npm run create-admin
```

Роли:

| Роль | Разрешения |
|---|---|
| `admin` | Полный доступ и управление токенами доступа |
| `operator` | Управление обновлениями и аварийными маршрутами |
| `viewer` | Только чтение |

Пароли должны содержать минимум 12 символов. Хранятся только bcrypt-хеши.

## 5. Ручной запуск {#_5-manual-startup}

До запуска создайте [пару ключей подписи](./expo-app-setup.md#_2-create-the-code-signing-certificate) и задайте в `CODE_SIGNING_PRIVATE_KEY_PATH` абсолютный путь к закрытому ключу. Процесс сервера должен иметь право чтения; публичный сертификат сохраните для приложения. Эндпоинт состояния ниже проверяет БД, а не готовность подписи или хранилища.

```bash
npm ci
npm run build
npm run start
```

Готовность:

```bash
curl -fsS http://localhost:3000/api/health
```

Ожидаемый ответ:

```json
{
  "status": "ok",
  "checks": {
    "database": "ok"
  }
}
```

## 6. Быстрый запуск Docker Compose {#_6-docker-compose-quick-start}

```bash
cp .env.docker.example .env
```

Замените оба пароля в `.env`. До запуска создайте или скопируйте закрытый ключ подписи:

```bash
mkdir -p secrets
cp /secure/path/code-signing-private-key.pem \
  secrets/code-signing-private-key.pem
chmod 600 secrets/code-signing-private-key.pem
```

Затем запустите стек:

```bash
docker compose up -d --build
docker compose ps
```

Если порт `3000` занят, обновите оба значения в `.env`:

```env
OTA_HTTP_PORT=3100
OTA_PUBLIC_BASE_URL=http://localhost:3100
```

Сервисы:

- админка и OTA-сервер: `http://localhost:3000`;
- консоль MinIO: `http://localhost:9001`;
- PostgreSQL и MinIO API доступны только внутри сети Compose.

Закрытый ключ монтируется только для чтения в `/run/secrets/ota/code-signing-private-key.pem`. Публичный сертификат должен находиться в каждом приложении Expo, а не в контейнере сервера.

На новом томе PostgreSQL автоматически применяется `docs/migrations/schema.sql`. Создайте первого администратора внутри контейнера приложения:

```bash
docker compose exec app npm run create-admin
```

Остановка без удаления данных:

```bash
docker compose down
```

Удаляйте локальную БД и объектное хранилище только при намеренном полном сбросе:

```bash
docker compose down --volumes
```

Изменение `POSTGRES_PASSWORD` в `.env` не меняет пароль роли в существующем томе PostgreSQL. Синхронизируйте его без удаления данных:

```bash
npm run docker:sync-db-password
docker compose restart app
```

## 7. Токены доступа {#_7-access-tokens}

Токены доступа предназначены для CI, скриптов и будущего CLI публикации. Мобильные устройства их не отправляют.

Создавайте их через `POST /api/admin/access-tokens` с авторизацией `admin`. Сразу сохраните возвращённый исходный токен: он показывается только один раз.

Пример:

```bash
curl \
  -H "Authorization: Bearer $OTA_ACCESS_TOKEN" \
  https://updates.example.com/api/admin/updates
```

Доступные разрешения:

- `updates:read`;
- `updates:write`;
- `redirects:read`;
- `redirects:write`.

Немедленно отзывайте неиспользуемые или раскрытые токены.

## 8. Обновления и откат {#_8-updates-and-rollback}

Список обновлений находится в `/updates`.

- **Деактивировать** прекращает выдачу обновления.
- **Откат** закрепляет канал за более старым активным обновлением.
- **Вернуть последнее** завершает режим отката и возобновляет выдачу последнего обновления.
- При обычной работе не редактируйте указатели каналов напрямую в PostgreSQL.

После отката проверьте обе платформы и точную область runtime/канала.

## 9. Аварийные маршруты {#_9-emergency-redirects}

Правила управляются в `/updates/emergency-redirects`.

Сначала используйте `pinned`:

1. Укажите точные ID встроенного обновления, runtime, платформу и исходный канал.
2. Задайте правильный целевой канал.
3. Закрепите ID проверенного обновления для восстановления.
4. Убедитесь, что затронутая сборка получает и запускает OTA восстановления.
5. Переключитесь в `follow`, чтобы старая сборка получала будущие обновления целевого канала.

При переходе со старой JSON-конфигурации:

```bash
npm run emergency:import
```

После миграции обработчик манифестов читает только `ota_emergency_redirects`.

## 9.1 Глобальный аварийный переключатель OTA {#_9-1-global-ota-emergency-switch}

Основной элемент управления на `/updates` — переключатель инцидента с наивысшим приоритетом. В состоянии **BLOCKED**:

- каждый запрос манифеста получает подписанную директиву Expo `noUpdateAvailable`;
- каждый запрос `/api/assets` закрывает выдачу с `503` и `Cache-Control: no-store`;
- активация, откат, возврат к последнему и распространяющие изменения `channel-latest.json` / `update-meta.json` возвращают `409`;
- активация обновлений и изменения распространения каналов также отклоняются PostgreSQL с SQLSTATE `P0OTA` и сообщением `OTA_DISTRIBUTION_BLOCKED`, включая обычные прямые SQL-записи;
- деактивация, добавление неактивных черновиков, безопасное редактирование метаданных и очистка указателей каналов, не оставляющая выдаваемого обновления, доступны. Удаление обновления доступно только тогда, когда очистка указателей внешних ключей не продвинет и не перенаправит другое обновление.

Включение требует причины и подтверждения. Выключение тоже требует подтверждения. Наблюдатели видят состояние, но не могут его менять. Изменения используют оптимистическую версию и записываются с исполнителем и временем. RPC переключателя и триггеры распространения разделяют транзакционную блокировку БД: параллельное изменение либо завершается до BLOCKED, либо ждёт и отклоняется; окна между проверкой и изменением нет. Не отключайте эти триггеры во время инцидента.

Порядок действий при инциденте:

1. Откройте `/updates`, укажите инцидент/задачу и влияние в причине, затем выберите **Остановить все OTA**.
2. Подтвердите результат проверки манифеста (`noUpdateAvailable`) и ранее выданного URL `/api/assets` (`503`, no-store).
3. Исследуйте или деактивируйте проблемные обновления при заблокированном распространении.
4. Перед возобновлением проверьте указатели каналов и обе платформы.
5. Выберите **Возобновить OTA**, подтвердите и повторите проверки манифестов.

Переключатель требует миграции `docs/migrations/2026-09-02-ota-distribution-control.sql`. Отсутствующая таблица или ошибка чтения БД намеренно не трактуются как ACTIVE: выдача манифестов и ресурсов закрывается.

`OTA_CDN_BASE_URL` сохранён только как устаревшая настройка. Новые манифесты всегда используют проверяемые URL `/api/assets` сервера. Внешний CDN размещайте перед OTA-сервером, а не открывайте URL бакета, и убедитесь, что CDN соблюдает ответ `private, no-store`. Переключатель не отзывает неизменяемые старые URL хранилища/CDN, уже выданные прежней версией сервера; очистите или отключите старый CDN, прежде чем полагаться на переключатель для этих манифестов.

## 10. Резервные копии {#_10-backups}

PostgreSQL:

```bash
pg_dump --format=custom "$DATABASE_URL" > ota-database.dump
```

Восстановление в пустую БД:

```bash
pg_restore --clean --if-exists --dbname="$DATABASE_URL" ota-database.dump
```

Объектное хранилище нужно копировать отдельно средствами репликации, версионирования или S3-синхронизации провайдера. Резервной копии БД без ресурсов недостаточно для восстановления доставки OTA.

Для томов Docker:

```bash
docker compose exec -T postgres \
  pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=custom \
  > ota-database.dump
```

## 11. Безопасный порядок обновления {#_11-safe-upgrade-order}

1. Создайте резервные копии PostgreSQL и объектного хранилища.
2. Прочитайте новые файлы миграций.
3. Примените обратно совместимые миграции.
4. Выполните тесты и соберите новый образ.
5. Разверните приложение.
6. Проверьте `/api/health`.
7. Проверьте запросы манифестов production-областей iOS и Android.
8. Сохраните предыдущий образ для отката приложения.

Не развёртывайте код, читающий новую таблицу, до её создания.

### Миграция идентификаторов манифестов (2026-10-16) {#manifest-identity-migration-2026-10-16}

Примените `docs/migrations/2026-10-16-manifest-identity.sql` до развёртывания соответствующего серверного кода. Новые установки получают изменения из `schema.sql`. На существующих уже должна быть миграция управления распространением, описанная выше.

Для этого обновления остановите распространение OTA, примените миграцию, замените все экземпляры сервера и затем возобновите распространение. Не обслуживайте трафик смесью старых и новых экземпляров: старый код может вернуть манифест даже при ошибке асинхронной записи сопоставления. Откат к нему возвращает ошибку идентификации; одних новых SQL-триггеров недостаточно.

Каждый UUID манифеста теперь вычисляется из эпохи публикации канала и UUID реально выбранного обновления. Поэтому неактивная загрузка может использовать стабильное резервное обновление, не разделяя его ID манифеста с будущим активированным обновлением. Активация продвигает эпоху канала, даже если указатель latest не изменился. Изменения указателей и повторные откаты продвигают часы эпохи минимум на миллисекунду, сохраняя порядок публикаций для Expo.

Сервер записывает сопоставление манифеста с обновлением до возврата манифеста. Отсутствующие таблицы сопоставления, ошибки поиска или записи теперь завершают запрос ошибкой вместо незаметной смены ID или потери истории. Повтор одинакового сопоставления допустим; присвоение существующего ID манифеста другому обновлению или области отклоняется PostgreSQL. Ответам без обновления новое сопоставление не нужно.

Существующие записи сохраняются и читаются новым сервером. Ранее перезаписанные исторические сопоставления автоматически не восстанавливаются. Изменение защищает связь ID и обновления; оно не замораживает все опубликованные JSON/ресурсы и не меняет политику удаления или хранения. Текущие ID каналов в админке обозначают эпохи публикации, а не производные UUID, возвращаемые устройствам.

SQL-скрипт регрессии можно запустить на **одноразовой** БД после применения схемы и миграции:

```bash
psql "$OTA_TEST_DATABASE_URL" -v ON_ERROR_STOP=1 \
  -f scripts/tests/manifest-identity.sql
```

Он проверяет активацию черновиков, повторные активации/откаты, монотонность часов, глобальную защиту распространения и неизменяемые upsert-сопоставления. Он временно меняет глобальный переключатель и откатывает тестовые данные; не запускайте его на рабочей БД OTA.

## Телеметрия установок {#installation-telemetry}

После миграций идентификаторов манифестов и управления распространением выше примените файлы по порядку до развёртывания обновлённого сервера:

```sh
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 \
  -f docs/migrations/2026-10-19-device-heartbeat.sql \
  -f docs/migrations/2026-10-22-device-analytics.sql \
  -f docs/migrations/2026-10-22-device-version-metadata.sql \
  -f docs/migrations/2026-10-22-device-targeting.sql \
  -f docs/migrations/2026-10-22-device-targeting-activation.sql
```

Новые установки используют только `schema.sql`, уже содержащий изменения. Повторное применение сохраняет начало сбора, записи установок и аудитории релизов. Последняя миграция переносит публичную и адресную активацию в атомарную операцию БД, допускает очистку при деактивации во время глобальной остановки и добавляет отдельное действие `ota-force-update`. Примените её до соответствующего сервера.

Повторно запустите стандартный конфигуратор приложения для установки клиента идентификации/телеметрии и корневого подключения `useOtaUpdates`/`OtaUpdateGate`. Добавление SecureStore или других нативных зависимостей клиента требует нативной пересборки с совместимым runtime; не публикуйте JavaScript с импортом недоступных нативных модулей для старого runtime. Клиенты, уже отправляющие сигналы активности, могут заполнять аналитику без пересборки, но новые ID устройства и жизненный цикл хука требуют обновлённого клиента. См. [жизненный цикл клиента](./ota-client-lifecycle.md) и [выбор устройств](./device-targeting.md).

Страница **Установки** (`/updates/devices`) показывает текущие запуски по версиям, дневную активность и когорты. Дневная история начинается с миграции; история до обновления недоступна. Возвращаемость использует независимое окно 90 дней и полностью наблюдавшиеся последующие дни. Существующие установки остаются видимыми в когортах текущего состава. Точные правила фильтров и окон, проверки миграций, контракт событий, поведение точки входа, доступ и ограничения см. в [телеметрии установок](./installation-telemetry.md).
