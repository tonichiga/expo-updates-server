# OTA-релизы для выбранных устройств {#device-targeted-ota-releases}

У релиза есть аудитория (`all` или `devices`), независимая от политики доставки и Guard. Аудитория проверяется до выбора манифеста. Среда выполнения, канал и платформа по-прежнему должны совпадать. Guard принудительного обновления не обходит аудиторию.

## Сначала smoke-тест, затем релиз {#smoke-test-then-release}

1. Настройте приложение через `npm run configure-app`. Сгенерированный `ota-entry.js` запускает клиент до исходной точки входа Router или пользовательского приложения; ручное подключение хука или ID не требуется. Существующие сгенерированные файлы можно обновить с `--force` (проверьте локальные изменения).
2. Пересоберите нативное приложение после добавления `expo-secure-store`; используйте новую среду выполнения, чтобы старые сборки не скачивали JavaScript, импортирующий отсутствующий нативный модуль.
3. Откройте приложение. В **Установки → Детали установки** скопируйте ID устройства или назовите его **Мой телефон**. Старые клиенты по-прежнему сообщают ID установки, по которому их можно выбрать.
4. Опубликуйте через сгенерированную команду `npm run ota:publish -- --platform android --message "Smoke"`. Публикация создаёт черновик. В его деталях выберите **Аудитория обновления → Только выбранные устройства / установки**, укажите телефон и **сохраните до активации**.
5. Активируйте черновик. Ваше устройство получит его; другие совместимые устройства — предыдущее подходящее публичное обновление либо отсутствие обновления, если такого нет.
6. После проверки установите аудиторию **Все совместимые устройства** и сохраните. Тот же артефакт становится доступным всем; повторная публикация не нужна.

Изменение активной аудитории немедленно влияет на будущие проверки. Оно не удаляет и не отзывает кешированные или скачанные OTA-пакеты. Для изменения запущенной версии используйте существующий процесс отката. Выбор устройств — механизм распространения, а не аутентификация или конфиденциальное хранилище: изменённый клиент может передать ID, а URL ресурсов остаются доступными.

## Два идентификатора {#two-identities}

- **ID установки (Installation ID)**: случайный UUID в AsyncStorage. Сохраняется при OTA, меняется после удаления приложения или очистки данных. Остаётся единицей подсчёта аналитики установок и когорт.
- **ID устройства (Device ID)**: значение SHA-256 в области ID приложения и пространства имён OTA-сервера. На Android исходное значение — `expo-application.getAndroidId()` (ключ подписи + пользователь Android + устройство). На iOS это случайный UUID, сохранённый через `expo-secure-store` с `WHEN_UNLOCKED_THIS_DEVICE_ONLY`, чтобы восстановленная на другом телефоне резервная копия намеренно не переносила идентификатор. Исходные платформенные ID никогда не отправляются на сервер.

Переустановка Android с тем же ключом подписи обычно сохраняет ID устройства. Сброс к заводским настройкам, смена пользователя/профиля Android или ключа подписи могут изменить его. iOS Keychain часто сохраняется после переустановки с тем же bundle ID, но это не гарантируется. При смене ID устройства выберите новое устройство в аудитории повторно. Универсального постоянного идентификатора физического устройства нет. Имя в админке относится к ID устройства, а не установки.

`ota-client/config.json.identityNamespace` сохраняется при повторной настройке, включая смену URL сервера или туннеля. Храните этот сгенерированный файл вместе с исходниками приложения. Среда выполнения и канал намеренно не входят в ID устройства. Отдельному приложению или серверу нужно своё пространство имён.

Официальные справочники API: [Expo Application](https://docs.expo.dev/versions/v58.0.0/sdk/application/), [Expo SecureStore](https://docs.expo.dev/versions/v58.0.0/sdk/securestore/), [дополнительные параметры Expo](https://docs.expo.dev/versions/v58.0.0/sdk/updates/#updatessetextraparamasynckey-value).

## Инициализация клиента {#client-initialization}

Сгенерированная точка входа автоматически вызывает `start()`, сохраняет идентификатор установки и задаёт `installation_id` / `device_id` через `Updates.setExtraParamAsync`. Сигнал активности добавляет необязательный `deviceId`. Надёжная очередь и монотонная последовательность для каждой установки не меняются. Недоступный ID устройства не останавливает телеметрию установок; доставка по устройствам при этом закрыта. После временного сбоя Keychain чтение ID на iOS повторяется без замены исходного значения.

Для собственного интерфейса проверки и скачивания используйте сгенерированные `checkForUpdateAsync` и `fetchUpdateAsync`: они ждут инициализации. Прямые вызовы `expo-updates` до инициализации могут сделать анонимную проверку; анонимные клиенты получают только публичные обновления. Конфигурация задаёт `checkAutomatically: NEVER`, сохраняя явное управление проверками. Сам инициализатор не скачивает обновления, не перезапускает приложение и не меняет навигацию.

Необязательные экспорты `getInstallationId()` / `getDeviceId()` нужны для отображения диагностики, а не для регистрации устройства. Оба возвращают null, когда обновления отключены (web/dev).

## Миграция и поведение сервера {#server-migration-and-behavior}

Примените `docs/migrations/2026-10-22-device-targeting.sql` после миграций аналитики и версий, до развёртывания сервера. Новые установки используют `docs/migrations/schema.sql`. Затем примените `docs/migrations/2026-10-22-device-targeting-activation.sql` до развёртывания серверных изменений по итогам перекрёстного ревью. Она атомарно применяет правила публичной и адресной активации, сохраняет деактивацию во время глобальной остановки и добавляет действие `ota-force-update` рядом с отдельным действием нативного обновления через магазин. Обе миграции повторяемы и не меняют аудиторию или активность существующих релизов.

Миграция аудитории удаляет индекс единственного активного релиза: адресный релиз должен сосуществовать с публичным резервным. У существующих релизов аудитория `all`.

Активация, откат и возврат к последней версии адресного релиза сохраняют другие активные релизы. Обычная публичная активация по-прежнему отключает старые релизы. Расширение уже активного адресного релиза оставляет предыдущий публичный резервный релиз подходящим; при выборе выигрывает более новый. Отключение адресного релиза возвращает выбор резервного. Явный откат приоритетен, но подчиняется тем же проверкам аудитории и совместимости. Аварийные закреплённые маршруты по-прежнему закрывают выдачу, если выбранный артефакт отличается.

API админки:

- `GET/PUT /api/admin/updates/:encodedKey/audience` использует существующие разрешения чтения и записи. PUT заменяет режим и оба списка ID, используя `audience_version` для оптимистической конкуренции. В режиме `devices` нужен хотя бы один адресат; максимум 100 ID каждого типа. БД сериализует изменения аудитории с аварийным переключателем распространения.
- `GET /api/admin/device-targets?platform=android|ios` требует сессии админки и возвращает последние 500 установок, включая старые среды выполнения. Поиск интерфейса показывает до 50 совпадений; более старые ID можно ввести вручную.
- `PUT /api/admin/device-targets` задаёт имя ID устройства (только сессия admin/operator).

Запросы манифеста читают Expo Structured Field Dictionary `Expo-Extra-Params`. Отсутствующие или некорректные ID никогда не совпадают с закрытой аудиторией. Ответы используют `private, no-store`. Пригодность проверяется до запроса резервного последнего активного обновления, а не после выбора одной нефильтрованной строки. Принятые сигналы активности могут связать новую установку с тем же ID устройства; повторные и устаревшие события не меняют связь и не объединяют историю установок.

Для изолированных локальных конфигураций Docker `configure-app --server-env .env.ota-test` использует опубликованные порты БД и хранилища из этого файла при создании `.env.ota`.

## Проверка {#verification}

`npm test`, `npm run lint`, `npx tsc --noEmit` и `npm run installer:check` проверяют сервер и упаковку. Запустите `OTA_TEST_DATABASE_URL=... node scripts/tests/device-targeting.mjs` на одноразовой тестовой БД с миграциями для реальных проверок PostgreSQL: пригодность, совместимость, CAS, глобальная блокировка и переустановка. Тестовые данные откатываются. Поведение переустановки и Keychain дополнительно требует физических устройств с нативной сборкой.

Активация и изменение аудитории сериализованы в PostgreSQL. Публичная активация отключает другие активные релизы той же области одним SQL-выражением; неудачная активация не может частично отключить предыдущий публичный релиз. Это касается и существующего редактора `update-meta.json`. Адресная активация сохраняет другие аудитории. Во время глобальной остановки деактивация может исправить устаревшие указатели на оставшийся активный резервный релиз; активация, возврат с действующего отката и смена аудитории остаются заблокированными.

Запустите `scripts/tests/device-targeting-activation.mjs` на **пустой одноразовой БД** с полной схемой для проверки параллельных изменений аудитории, атомарности неудачной активации и деактивации при инциденте. Скрипт отклоняет БД с релизами. Исполнитель миграций аналитики также запускает этот набор для новых установок и обновлений.
