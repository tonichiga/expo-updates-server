# Клиентский контракт политики OTA-обновлений {#ota-update-policy-client-contract}

Каждый выдаваемый манифест обновления содержит `extra.updatePolicy`:

```json
{
  "schemaVersion": 1,
  "policyVersion": 2,
  "delivery": "background",
  "guard": {
    "action": "require-confirmation",
    "payload": { "message": "Restart when ready" }
  }
}
```

Свойство `guard` отсутствует, если Guard не настроен. Настроенный Guard безусловен: он включается для каждого клиента, которому существующая логика выбора по среде выполнения, каналу, платформе, аудитории и обновлению выдаёт это OTA. Принудительный Guard никогда не обходит аудиторию устройств. Наличие действия в каталоге рекомендательное и не требуется для его сохранения или выдачи.

- `Updates.checkForUpdateAsync()` возвращает политику в манифесте **кандидата** в результате проверки.
- `Updates.manifest` содержит политику обновления, **запущенного сейчас**. Не используйте её как политику кандидата до скачивания.
- `manual` используется по умолчанию и оставляет скачивание и перезапуск приложению.
- `background` означает незаметное скачивание кандидата без немедленного перезапуска и применение при следующем холодном старте.
- Старые клиенты безопасно игнорируют дополнительное значение `extra`.

Неактивная загрузка является черновиком, даже если её начальный `disabled_at` равен `created_at`. Режим доставки и простой Guard можно редактировать до активации. Сам по себе `disabled_at` не доказывает, что обновление публиковалось.

`ota_update_channels.latest_update_id` обозначает новейшую загрузку и потому может указывать на неактивный черновик. Этот указатель не доказывает публикацию; при выборе манифеста используется последнее активное обновление. Указатель отката `active_update_id` или запись в `ota_served_manifest_log` подтверждают публикацию.

Активация является событием публикации. После активации, возврата к последней версии, использования как цели отката или подтверждённой выдачи политика остаётся неизменяемой, даже если затем обновление отключили. Чтобы изменить политику, опубликуйте новый ID обновления.

## Порядок обновления production {#production-upgrade-order}

Создайте резервную копию БД. Для существующих установок примените эти идемпотентные миграции по порядку:

```bash
psql "$DATABASE_URL" -f docs/migrations/2026-09-01-p1-guard-actions.sql
psql "$DATABASE_URL" -f docs/migrations/2026-09-01-p2-simplify-ota-guard-policy.sql
psql "$DATABASE_URL" -f docs/migrations/2026-09-01-policy-publication-correction.sql
```

Миграция упрощения намеренно удаляет `guard_rules` без преобразования старых правил. Она добавляет допускающие null столбцы `guard_action` и `guard_payload` и пересоздаёт триггер неизменяемости политики для простой модели. Последняя корректирующая миграция очищает только ошибочно определённые маркеры публикации для консервативно выбранных неактивных стандартных политик, которые никогда не выдавались. Она не разблокирует активные обновления, цели отката или уже выданные обновления.

Окружения, где уже успешно выполнена `2026-09-01-policy-publication-correction.sql` и подтверждено отсутствие черновиков, ошибочно отмеченных опубликованными, могут пропустить третий шаг. Иначе коррекция должна идти третьей, так как обращается к столбцам `guard_action` и `guard_payload`, созданным миграцией упрощения.

Пользователи Supabase могут выполнить те же файлы в SQL Editor в указанном порядке. Для новых установок применяйте только канонический `docs/migrations/schema.sql`, уже содержащий простую модель.

## Каталог действий Guard {#guard-action-catalog}

Редактор политики загружает повторно используемые имена действий из `ota_guard_actions`. Новые установки получают отдельные действия `ota-force-update` и `ota-force-store-update`. Операторы могут создать действие, введя его в поле выбора, или через отдельную форму каталога. Эта форма доступна и при просмотре неизменяемой политики и никогда её не меняет.

Сохранённые записи каталога можно удалить кнопкой корзины. Удаление из каталога не меняет существующую политику. Её действие остаётся видимым как временный вариант до явного изменения; у таких вариантов нет кнопки удаления.

При создании ключи действий обрезаются по краям, должны содержать 1–100 символов и не могут содержать управляющих символов. Наблюдатели могут просматривать каталог, но не создавать и не удалять записи.

## Сгенерированный клиентский хук {#generated-client-hook}

Конфигуратор устанавливает `useOtaUpdates(options)` и автоматически подключает его в корневом layout/App с `OtaUpdateGate` вокруг содержимого приложения. Настройки и методы описаны в [руководстве по жизненному циклу клиента](./ota-client-lifecycle.md). Хук оценивает политику кандидата из `check()`, затем повторно проверяет скачанный манифест: выбранный релиз может измениться между проверкой и скачиванием.

- `ota-force-update` требует совместимое **OTA**: блокирующий экран запрещает взаимодействие, хук скачивает обновление и показывает действие перезапуска после готовности.
- `ota-force-store-update` требует **новую нативную сборку**: экран открывает URL магазина для платформы и не скачивает этого OTA-кандидата. OTA не может изменить среду выполнения или добавить нативные модули. Дополнительные данные поддерживают `androidUrl`, `iosUrl` либо общий резервный `url`.
- Неизвестные и пользовательские действия остаются заблокированными, пока явный `guardHandlers[action]` не вернёт `allow`. Сама запись в каталоге не реализует поведение Guard.
- `delivery: background` скачивает незаметно и ждёт холодного запуска или ручного перезапуска. Включённый `autoReload` не вызывает немедленный перезапуск.
- Кандидат с ручной доставкой показывается для явного скачивания и перезапуска, если корневые настройки не включают `autoUpdate`/`autoReload`. Сгенерированный корень включает только автоматические проверки.

Блокирующий экран необходим для блокировки интерфейса приложения; один хук лишь предоставляет состояние. Пока обязательный кандидат не обнаружен, ошибка проверки без сети оставляет работающее приложение доступным. Expo может применить ранее скачанный пакет при нативном запуске; JavaScript не может отозвать этот нативный кеш. Это политики доставки, а не аутентификация клиента. Старые клиенты могут игнорировать поля политики, поэтому сначала распространите настроенный нативный клиент и только затем полагайтесь на Guard.

Существующие установки получают новое действие OTA Guard через `2026-10-22-device-targeting-activation.sql`, после миграций аудитории из [руководства по эксплуатации](./operations-guide.md#installation-telemetry). Миграция идемпотентна и не переписывает опубликованные политики.
