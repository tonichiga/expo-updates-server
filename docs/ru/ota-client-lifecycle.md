# Жизненный цикл сгенерированного OTA-клиента {#generated-ota-client-lifecycle}

`configure-app` генерирует отформатированный TypeScript-клиент и размещает `<OtaUpdates />` рядом с навигацией в корневом layout/App. Компонент вызывает `useOtaUpdates` внутри; он не оборачивает приложение и не предоставляет React-контекст. Монтируйте его один раз в постоянном корне, включая ветки загрузки и раннего возврата.

По умолчанию он автоматически проверяет обновления и предлагает **Download / Later** для обычного обновления, а после скачивания — **Restart / Later**. `autoUpdate={false}` отключает автоматическое скачивание, но не предложение. Отклонённый кандидат скрыт до повторного монтирования, появления другого кандидата или изменения состояния скачивания. Фоновые обновления остаются незаметными; обязательные нельзя отклонить.

Низкоуровневый `useOtaUpdates()` доступен для необязательных собственных экранов. Он разделяет состояние и действия, но по умолчанию не автоматизирует их и не выводит интерфейс. Настраивайте автоматизацию в одном корне; несколько настроенных потребителей объединяют логические параметры через OR. Сохраняйте стабильность собственных обработчиков Guard.

Идентификаторы сохраняются и устанавливаются в параметры запросов Expo до любой проверки или скачивания. Сигналы запуска и возврата на передний план сообщают только **запущенный** пакет, а не скачанного кандидата. Сетевая телеметрия не блокирует запуск или проверку обновлений. В режиме разработки, Expo Go, web и сборках с отключёнными обновлениями автоматизация выключена.

| Политика/параметры | Поведение |
| --- | --- |
| manual, стандартные параметры | OtaUpdates предлагает скачивание/перезапуск; один хук предоставляет состояние |
| autoCheck | Проверка при монтировании и выходе на передний план, минимальный интервал 60 секунд |
| autoUpdate | Также скачивает подходящих кандидатов с ручной доставкой |
| autoReload | Перезапускает ожидающий нефоновый пакет, когда приложение активно |
| delivery=background | Незаметно скачивает; применяет при следующем холодном запуске или ручном перезапуске |
| guard=ota-force-update | Блокирует экраном, автоматически скачивает; после готовности показывает кнопку перезапуска |
| guard=ota-force-store-update | Блокирует экраном; открывает магазин, никогда не скачивает этого кандидата |
| собственный/неизвестный Guard | Блокирует, пока guardHandlers[action] явно не вернёт `allow` |

Данные Guard магазина: `{ "androidUrl": "market://details?id=com.example.app", "iosUrl": "https://apps.apple.com/app/id123" }`; `url` — общий резервный вариант. Допускаются только URL https, market и itms-apps. Нативное обновление по-прежнему требует релиза в магазине; OTA не может добавить нативные модули или изменить установленный runtime.

Встроенный блокирующий экран — незакрываемое модальное окно, сохраняющее смонтированную навигацию и провайдеры. Настройте обязательный интерфейс через `renderBlocked`, необязательный — через `renderAvailable`. Оставляйте `OtaUpdates` рядом с навигацией; один хук предоставляет `blocked`, но не предотвращает взаимодействие с вашими экранами. Неизвестные Guard закрывают доступ. Обязательные проверки — сетевая политика, а не аутентификация или защита от вмешательства. Ошибка проверки без сети оставляет приложение доступным, если обязательный кандидат ещё не обнаружен и запущенный пакет не требует Guard магазина или собственного Guard.

Одновременно выполняется один вызов каждого действия; другое действие во время занятости отклоняется. Ошибки доступны в `error`, возвращаемые Promise отклоняются, поэтому ручные вызовы обрабатывайте через try/catch. Повторная попытка снова проверяет сервер и пересматривает собственный Guard ожидающего кандидата. Скачивание повторно оценивает политику полученного манифеста: она может отличаться от проверенного кандидата. Ожидающий пакет управляет блокирующим экраном до перезапуска; проверка другого кандидата не разрешает старый кешированный пакет. Поддерживаются нативные директивы отката. Expo управляет загрузкой уже скачанных пакетов при холодном старте; JS Guard не может отозвать этот нативный кеш. Guard магазина и собственные Guard повторно проверяются по запущенному манифесту на следующем запуске; требование принудительного OTA уже выполнено запуском этого пакета. Не смешивайте прямые вызовы expo-updates или нативные автоматические проверки с управлением хуком: configure-app использует checkAutomatically=NEVER.

Старые экспорты `checkForUpdateAsync`/`fetchUpdateAsync` остаются низкоуровневыми API с учётом идентификаторов для существующих интеграций. Они намеренно не реализуют политики хука. Учётные данные БД или админки в приложение не попадают: сервер сохраняет публичные сигналы активности.

## Подключение и настройка {#integration-and-customization}

Выполните стандартную `npm run configure-app -- ...` из проекта сервера. Она сохраняет исходную точку входа, генерирует клиент и вставляет самостоятельный компонент в поддерживаемые корневые компоненты. Для Expo Router это `src/app/_layout` (приоритетен при наличии `src/app`) или `app/_layout`, включая платформенные варианты. Для стандартной точки входа — `App`, если собственный `index` не регистрирует другой корень. Синхронные функциональные компоненты и поддерживаемые формы экспорта по умолчанию изменяются без изменения навигации. Неподдерживаемая форма корня отклоняется до записи; неопределимый пользовательский корень сохраняет автоматические идентификацию/телеметрию и получает предупреждение о ручном подключении жизненного цикла. Сгенерированное подключение начинается с:

```tsx
return (
  <>
    <OtaUpdates autoCheck autoUpdate={false} autoReload={false} />
    <AppTabs />
  </>
);
```

Меняйте эти параметры в корневом компоненте. На других экранах используйте `useOtaUpdates()` для ручного управления и общего состояния. Конфигуратор выбирает подходящий путь импорта; учётные данные БД и админки не должны попадать в приложение. Сгенерированные исходники включают `ota-client/docs/update-lifecycle.md` с этим контрактом для разработчиков приложения.

Для уже настроенного проекта проверьте изменения сгенерированных файлов и повторите с `--force`. Это заменяет старые JavaScript-файлы на TypeScript, удаляет устаревшие копии `.js`/`.d.ts`, способные перекрывать новые модули, и переносит стандартный корневой хук/экран с сохранением параметров. Код со старым корневым контроллером или собственным блокирующим экраном переносится вручную; предварительная проверка останавливает процесс до любых записей. Используйте `.tsx` для корней TypeScript JSX. Существующие потребители `OtaUpdateGate` поддерживаются. Нативные зависимости требуют новой сборки; используйте новый runtime, если старые установленные сборки не имеют этих модулей. Публикация остаётся через сгенерированную `npm run ota:publish`. См. [выбор устройств](./device-targeting.md) для smoke-аудитории и [телеметрию установок](./installation-telemetry.md) для правил получения событий и аналитики.

## Ручное подключение {#manual-integration}

Используйте этот путь, если `configure-app` не может изменить корневой компонент, проект использует динамический `app.config.*` или вы хотите подключить клиент самостоятельно. Хук — исходный код из этого репозитория, **а не npm-пакет**. Не импортируйте его из `expo-updates`.

### 1. Подготовьте клиент и нативную конфигурацию {#_1-prepare-the-client-and-native-configuration}

Если после настройки уже есть `ota-client/index.ts`, `ota-client/types.ts` и `ota-client/config.json`, сохраните их и переходите к шагу 2. Предупреждение о неопределимом пользовательском корне означает, что начальная загрузка и клиент установлены; ошибка неподдерживаемого корня останавливает настройку до записи, поэтому проверьте реальные файлы.

Для приложения без сгенерированного клиента выполните из каталога приложения:

```bash
npx expo install expo-updates expo-application expo-crypto expo-secure-store @react-native-async-storage/async-storage
```

Скопируйте **весь** каталог `templates/expo-app/ota-client/` из репозитория OTA-сервера в `<application>/ota-client/`. Сохраните вместе вложенные `model/`, `ui/`, файлы выполнения, идентификации, телеметрии и типов. Например, если такого каталога в приложении ещё нет:

```bash
cp -R /full/path/to/expo-updates-server/templates/expo-app/ota-client ./ota-client
```

Создайте `<application>/ota-client/config.json`:

```json
{
  "channel": "preview",
  "heartbeatUrl": "https://updates.example.com/api/device-heartbeat",
  "identityNamespace": "https://updates.example.com"
}
```

Используйте реальный URL сервера. `channel` должен совпадать с нативным заголовком запроса `expo-channel-name`. `identityNamespace` — стабильная область идентификации: сохраняйте существующее значение при смене туннеля/домена, runtime или канала. Секрета здесь нет. Не копируйте в файл ID установки, ID устройства, пароль БД или токен админки: клиент сам создаёт идентификаторы и отправляет публичные сигналы активности.

Завершите [нативную конфигурацию Expo](./expo-app-setup.md#_3-configure-the-expo-application): URL манифеста сервера, соответствующий публичный сертификат, runtime и канал. Задайте `updates.checkAutomatically` как `NEVER`; проверки должны ждать настройки идентификаторов. Храните закрытый ключ подписи и данные публикатора вне мобильного пакета. Динамическая конфигурация должна вычислять тот же канал, что в `ota-client/config.json`.

### 2. Подключите корневой layout или App {#_2-connect-the-root-layout-or-app}

Для Expo Router разместите компонент рядом с навигацией в существующем `src/app/_layout.tsx`. Сохраните провайдеры, шрифты, обработку заставки и другой код layout. Не помещайте компонент в коллекции дочерних элементов только для навигатора, такие как `Stack.Screen`/`Tabs.Screen`.

```tsx
import { Stack } from 'expo-router';
import { OtaUpdates } from '../../ota-client';

export default function RootLayout() {
  return (
    <>
      <OtaUpdates autoCheck autoUpdate={false} autoReload={false} />
      <Stack />
    </>
  );
}
```

Скорректируйте относительный импорт по расположению файла:

| Корневой файл | Путь импорта |
| --- | --- |
| `src/app/_layout.tsx` | `../../ota-client` |
| `app/_layout.tsx` | `../ota-client` |
| `App.tsx` в корне приложения | `./ota-client` |

Для приложения без Router разместите тот же компонент рядом с существующим содержимым. Он может быть соседом классового компонента. Монтируйте один экземпляр, включая загрузку и ранние возвраты. Собственная точка входа по-прежнему регистрирует исходный корень.

Сохраните существующий сгенерированный `ota-entry.js` и его настройку `package.json.main`. При полностью ручном подключении менять точку входа **не требуется**: смонтированный хук сам вызывает идемпотентный `start()` телеметрии. Идентификаторы сохраняются до запросов обновления; сетевые ошибки сигналов активности не блокируют отображение и проверки. Не добавляйте другую реализацию телеметрии и не вызывайте проверки Expo при инициализации модуля. Если регистрация нужна до монтирования корня, публичный `start()` также можно вызвать в существующей точке входа, не заменяя исходный код регистрации.

`OtaUpdates` предоставляет стандартный интерфейс принудительного обновления. При использовании только хука нужен собственный интерфейс, применяющий `blocked`. Свой блокирующий экран поддерживается через `renderBlocked`; это не меняет решение Guard контроллера.

### 3. Добавьте ручное управление обновлениями {#_3-add-manual-update-controls}

Корень уже предоставляет элементы скачивания/перезапуска. Отдельный экран настроек необязателен и может подписаться без включения ещё одного автоматического процесса. Например, `src/components/ota-controls.tsx`:

```tsx
import { useState } from 'react';
import { Button, Text, View } from 'react-native';
import { useOtaUpdates } from '../../ota-client';

export function OtaControls() {
  const ota = useOtaUpdates();
  const [message, setMessage] = useState('');

  async function perform(action: () => Promise<unknown>) {
    try {
      setMessage('');
      await action();
    } catch (error) {
      setMessage(error instanceof Error ? error.message : String(error));
    }
  }

  return (
    <View>
      <Text>Installation: {ota.installationId ?? 'Initializing'}</Text>
      <Text>Device: {ota.deviceId ?? 'Unavailable'}</Text>
      <Text>State: {ota.status}</Text>
      <Text accessibilityLiveRegion="polite">{message || ota.error?.message}</Text>
      <Button title="Check OTA" disabled={!ota.enabled || ota.isBusy}
        onPress={() => { void perform(ota.check); }} />
      <Button title="Download OTA"
        disabled={!ota.enabled || ota.isBusy || !ota.available || ota.pending || ota.blocked}
        onPress={() => { void perform(ota.download); }} />
      <Button title="Restart with OTA"
        disabled={!ota.enabled || ota.isBusy || !ota.pending || ota.blocked}
        onPress={() => { void perform(ota.reload); }} />
    </View>
  );
}
```

Блокирующий экран предоставляет действия обязательного обновления, пока обычные экранные элементы заблокированы. Для автоматического скачивания обычных обновлений задайте `autoUpdate: true` в корне; добавляйте `autoReload: true`, только если приложению подходят автоматические перезапуски на переднем плане. Серверная доставка `background` по-прежнему запрещает немедленный автоматический перезапуск. Собственные Guard требуют явного решения `guardHandlers[action]`; возврат `allow` должен следовать реальному условию приложения, а не просто скрывать неизвестное действие.

### 4. Пересоберите и проверьте {#_4-rebuild-and-verify}

После добавления нативных зависимостей или смены URL/runtime/канала/сертификата выполните prebuild и установите новую релизную сборку. Используйте окружение, требуемое динамической конфигурацией, при запуске команд Expo. Expo Go и обычный режим разработки не проверяют жизненный цикл телеметрии/обновлений этого клиента.

1. Проверьте TypeScript и lint, затем соберите и установите релиз.
2. Запустите его и убедитесь, что установка появилась в `/updates/devices`.
3. Опубликуйте новое OTA **после** сборки нативного приложения для его точной области, затем активируйте.
4. Проверьте → скачайте → перезапустите; подтвердите новую запущенную версию в админке.
5. Убедитесь, что ID установки не изменился после OTA. Переустановка может изменить его; сохранение ID устройства имеет [платформенные ограничения](./device-targeting.md).
6. Отдельно проверьте фоновую доставку, принудительное OTA, обновление из магазина и собственные Guard.

Копирование `ota-client/` и добавление хука не устанавливают скрипты публикатора и регистрацию встроенных сборок. Это отдельные шаги [руководства по приложению](./expo-app-setup.md#_6-register-embedded-updates). Если автоматический конфигуратор уже их установил, продолжайте использовать его `npm run ota:publish`. Встроенный публикатор читает только статический `app.json`: ручное подключение хука не делает проект с динамическим `app.config.*` поддерживаемым сквозным процессом публикации. Таким проектам нужна отдельная интеграция публикации и сборки до шага 3 выше.
